Detailed Description

Check digits of financial and retail identifiers, validated and computed at compile time: Luhn, ISIN (ISO 6166), IBAN (ISO 13616, MOD 97-10), LEI (ISO 17442, MOD 97-10), CUSIP, SEDOL and GTIN (EAN-13, EAN-8, UPC-A).

Overview. An identifier typed, pasted or received is checked before it is trusted: one wrong character and the check digits no longer match. For each scheme there is a validate_<scheme>(text), which checks the shape and the check digits and returns result<void, identifier_errc>, and a <scheme>_check_digit(s), which computes them for the identifier's body:

  • Luhn (ISO/IEC 7812-1): a string of decimal digits whose last is the Luhn check digit (card numbers, IMEIs);
  • ISIN: two letters, nine letters or digits, one Luhn check digit over the letters spelled as numbers (A = 10);
  • IBAN: two letters (the country), two check digits, a basic bank account number (BBAN) of 1 to 30 letters or digits; the whole read as a number with the first four characters moved to the end is 1 modulo 97;
  • LEI: eighteen letters or digits and two check digits, the whole 1 modulo 97 (ISO 7064 MOD 97-10);
  • CUSIP: eight letters, digits, *, @ or # and one check digit (doubling every second value);
  • SEDOL: six digits or consonants and one check digit (weights 1, 3, 1, 7, 3, 9); a SEDOL starting with a digit is digits throughout;
  • GTIN (GS1): EAN-8, UPC-A (GTIN-12), EAN-13 (GTIN-13) or GTIN-14, digits whose last is the GS1 mod-10 check digit (weights 3 and 1 from the right). The barcode on a retail product or a bill-payment slip; drawing the bars is not core's.

Text is strict: upper case only, no spaces or separators. Strip and upper-case before validating.

static_assert(validate_isin("US0378331005")); // Apple
static_assert(validate_iban("GB82WEST12345698765432"));
static_assert(validate_lei("5493001KJTIIGC8Y1R12"));
static_assert(validate_cusip("037833100") && validate_sedol("B0YBKJ7") && validate_luhn("4111111111111111"));
// a mistyped identifier is refused with the reason
const auto r = validate_isin("US0378331006");
// check digits for a new identifier's body
constexpr auto iban = iban_check_digits("DE", "370400440532013000"); // "89"

Relationships. result.hpp. ids/ holds identifiers and their checks; uuid.hpp and phone_number.hpp are identifiers with types of their own. Group: snicholls-core.

Implementations. One per scheme.

Guarantees. constexpr, noexcept, O(n), no allocation; MOD 97 is computed digit by digit, so no identifier is too long for the arithmetic.

Errors. identifier_errc:

  • wrong_length: the scheme's length is not met;
  • invalid_character: a character the scheme never uses (a lower-case letter, a space, a vowel in a SEDOL);
  • invalid_format: a usable character in the wrong place (a digit in an ISIN's or IBAN's country, a letter in a check digit, a letter after a SEDOL's leading digit);
  • invalid_check_digit: the check digits do not match, or an IBAN's are 00, 01 or 99, which ISO 13616 never issues.

Performance. benchmarks/ids/check_digits_benchmark.cpp: 4,096 identifiers, a quarter of them wrong, Release, Apple clang 17, Xeon W-3245, 2026-11-23: validate_isin 265 us against 287 us for the same checks written by hand, validate_iban (22 characters) 424 us against 434 us (about 65 and 104 ns an identifier).

Tests and demos. tests/ids/check_digits_test.cpp, against fixtures from python-stdnum 2.2 (scripts/generate_check_digit_fixtures.py, tests/fixtures/ids/check_digits.txt); demos/ids/check_digits_demo.cpp.

Dependencies. <array>, <cstdint>, <string_view>, result.hpp.

Known issues. Structure is checked, not registration:

  • an ISIN's first two letters are not checked against ISO 3166 (python-stdnum does check them);
  • an IBAN's BBAN length and format per country are not checked: they are data (the SWIFT IBAN Registry, revised several times a year), which by core's rule stays with the caller;
  • a LEI's issuer prefix is not checked.

Status. New in 0.23.0.
