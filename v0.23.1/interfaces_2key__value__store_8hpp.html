Detailed Description

The key-value store contract, virtual form: key_value_store_interface, kv_reader_interface and the adapters.

Overview. When the store is chosen at run time (a configuration file names the backend, a plugin provides it), code holds a key_value_store_interface&. Its pure virtual functions are exactly the operations of the concept key_value_store (concepts/key_value_store.hpp), so:

  • the interface itself models the concept: every function template written against the concept, the conveniences kv_get, kv_scan_prefix, kv_digest_v1 and the conformance kit included, takes it as it is;
  • key_value_store_adapter<S> puts any model of the concept behind the interface, owning it (S) or referring to it (S&); kv_reader_adapter<R> does the same for a read-only view, and is what an adapted store's snapshot() returns.
// The composition root chooses the backend (here from a name, in production from configuration) ...
std::unique_ptr<key_value_store_interface> open_store(std::string_view backend)
{
if (backend == "memory")
return std::make_unique<key_value_store_adapter<reference_key_value_store>>(reference_key_value_store{});
return nullptr; // above core: "rocksdb", "postgres", ...
}
// ... and application code sees only the interface, which models the concept, so the conveniences work on it.
bool record_login(key_value_store_interface& store, std::string_view user)
{
return kv_put(store, "login/" + std::string(user), "2026-11-23T09:00:00Z").is_ok();
}

Use the concept by default (static dispatch, inlined on in-memory stores); use the interface where the choice is made at run time or a compilation firewall is wanted. For an I/O-bound backend the virtual call is free; on the in-memory reference it is measured (Performance).

Relationships. The concept, the ranges, batches, errors and conveniences: concepts/key_value_store.hpp. The reference implementation: interfaces/key_value_store_reference.hpp. The kit: interfaces/key_value_store_conformance.hpp. The other capabilities' interfaces: kv_health_interface (interfaces/kv_health.hpp), kv_backup_interface (interfaces/kv_backup.hpp); a backend implements as many as it offers, and a caller holding one asks for another with dynamic_cast. Group: snicholls-core.

Implementations / variants. key_value_store_adapter<S> over any model; above core, crtp's backends derive from the interface directly.

Guarantees. Those of the concept, which every implementation keeps. The adapters add one: no exception of the adapted store crosses them. An exception from the model becomes kv_errc::out_of_memory (std::bad_alloc) or kv_errc::backend (anything else); an exception thrown by the caller's own visitor propagates unchanged. Adapters are as thread-safe as the store they adapt.

Errors. As the concept; see the adapters' translation above.

Examples. See the overview, and demos/interfaces/key_value_store_demo.cpp.

Performance. benchmarks/interfaces/key_value_store_benchmark.cpp compares a hand-written std::map, the concept path and the virtual path on reference_key_value_store: point reads, overwrites and a 100-key prefix scan. Numbers in BENCHMARKS.md (Release only).

Tests and demos. tests/interfaces/key_value_store_test.cpp (the kit through both forms, the adapters' exception translation), demos/interfaces/key_value_store_demo.cpp.

Dependencies. <cstddef>, <cstdint>, <memory>, <new>, <span>, <type_traits>, <utility>, and concepts/key_value_store.hpp.

Known issues. A visitor that swallows an exception of the store and throws another is indistinguishable from a visitor's own exception, and propagates.

Status. New in 0.22.0. Experimental until two real implementations pass the kit.
