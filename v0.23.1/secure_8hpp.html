Detailed Description

secure_wipe, which the optimiser may not remove, and constant_time_equal for MACs and digests.

Overview. Two small tools every use of a key or a MAC needs.

  • secure_wipe(span) zeroes memory that held a secret (a key, a password, a KDF's working memory) just before it goes out of scope or is freed. A plain memset or loop there is a dead store the optimiser may delete, because nothing reads the memory afterwards; secure_wipe writes through a volatile pointer, which it may not, followed by a compiler fence. In a constant expression it is an ordinary zero fill.
  • constant_time_equal(a, b) compares two byte sequences in time that depends only on their length, never on where they first differ, so an attacker who can time a MAC check cannot learn the correct tag a byte at a time. Use it, not ==, to check a MAC, a password hash or any digest an attacker chooses; hmac::verify uses it.
// Compare a presented token with the expected one in time that does not depend on where they differ
bool token_matches(const std::string& presented, const snicholls::digest<32>& expected_hash)
{
return snicholls::constant_time_equal(snicholls::sha256::hash(presented), expected_hash);
}
// Wipe a key before its memory is reused: a plain loop here is a dead store the optimiser may delete
void use_and_forget(std::array<std::byte, 32>& key)
{
// ... use the key ...
snicholls::secure_wipe(std::span<std::byte, 32>(key));
}

Relationships. hmac::verify (hash/hmac.hpp); scrypt (hash/scrypt.hpp), pbkdf2_hmac and hkdf_* (hash/kdf.hpp) wipe their intermediate keys with it; secret<T> (secret.hpp) wipes a string with it when it is destroyed. Group: snicholls-core.

Guarantees. Both are constexpr and noexcept. secure_wipe writes every byte of the span exactly once; it cannot reach copies the program made elsewhere (registers, spilled stack, a reallocated vector's old buffer), which no library function can. constant_time_equal returns false at once when the lengths differ (a length is not secret) and otherwise reads every byte of both, accumulating the differences with no branch on their values; the accumulator is read back through a volatile so the optimiser cannot turn the loop into an early exit.

Errors. None.

Examples. Above; demos/hash/secure_demo.cpp.

Performance. Not benchmarked: both are one pass over the bytes, and neither is on a hot path (a wipe ends a key's life, a comparison ends a MAC check).

Tests and demos. tests/hash/secure_test.cpp, demos/hash/secure_demo.cpp.

Dependencies. <cstddef>, <span>, <type_traits>, hash/digest.hpp, detail/hash_engine.hpp.

Known issues. Constant time is a property of the generated code, which the standard does not specify; this is the pattern libsodium and BoringSSL use for portable code, not a proof. Without platform headers there is no explicit_bzero, memset_s or SecureZeroMemory; the volatile loop is what they do.

Status. New in 0.17.0. Experimental.
