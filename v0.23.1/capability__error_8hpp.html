Detailed Description

snicholls::capability_error: the one error of every capability contract, its code capability_errc, is_retryable, and capability_result<V>.

Overview. The capability contracts (concepts/message_sender.hpp, concepts/signer.hpp, concepts/key_store.hpp, concepts/payment_provider.hpp, concepts/onramp_provider.hpp) fail the same way, so a caller writes its retry and alerting logic once:

  • one enumeration, capability_errc, for every capability. A caller branches on it: retry, tell the user, or page someone. Only unavailable, timeout and rate_limited are retryable (is_retryable). Its names print through core's enum reflection (enum_name(capability_errc::stale) is "stale"); there is no hand table;
  • capability_error is the code, the provider's own short code for the failure (provider_code, at most 32 characters of A-Z a-z 0-9 _ - . :: a Stripe decline_code, an OKX sCode, an HTTP status) and a fixed diagnostic (capability_message, at most 64 characters, from a string literal only). Neither holds a std::string: the error is trivially copyable, so returning one never allocates;
  • capability_result<V> is result<V, capability_error>; fail(code, provider_code, message) makes one.

Human detail belongs at the boundary, through snicholls::traced<capability_error> (traced.hpp), where a route or a worker adds its context and logs it.

const auto r = charge(true);
const capability_error& e = r.unwrap_err();
// a caller branches on the code; only unavailable, timeout and rate_limited are retried
const bool retry = e.retryable();
const std::string_view name = enum_name(e.code); // "rejected": names come from the enumeration itself
// a provider's raw response never becomes the error: only a short code survives
const capability_error from_response = provider_error(capability_errc::unavailable, "{\"message\":\"down for you@example.test\"}");
const auto code = provider_code::make("insufficient_funds"); // checked at run time

Relationships. result.hpp (result, err), containers/inplace_string.hpp (the storage), meta/enums.hpp (the names), capability_ids.hpp (the identifiers the contracts use), interfaces/capability_conformance.hpp (the kits' report and the redaction check). Group: snicholls-core.

Implementations / variants. One error for every capability; a capability that needs a finer reason says it in provider_code or message, never with an enumeration of its own.

Guarantees.

  • Everything is constexpr and noexcept; capability_error is trivially copyable and standard layout (static_asserted), 99 bytes.
  • The redaction rule. message holds fixed diagnostic text only: it can be made from a string literal and nothing else, so a provider's raw response body, user data (an address, a phone number, a message body, a one-time code) or a secret cannot reach it. provider_code is the provider's short error code only ("card_declined"): provider_code::make refuses text longer than 32 characters or with any character outside A-Z a-z 0-9 _ - . : (a space, a quote, a brace: free text and JSON), and provider_error drops such text rather than keep it. Every reference implementation honours the rule, and every conformance kit checks it (a provider failure whose response carries a marker; the marker must not appear in either field).
  • Refused, never truncated: a code that does not fit is not a shorter code.

Errors. provider_code::make returns capability_errc::invalid_argument for text that is not a provider code. A literal that is not one is a compile error.

Performance. Not benchmarked: the error path. No allocation by construction.

Tests and demos. tests/capability_error_test.cpp, demos/capability_error_demo.cpp.

Dependencies. <cstddef>, <cstdint>, <string_view>, <type_traits>, containers/inplace_string.hpp, result.hpp. The names come from meta/enums.hpp, which a caller that prints them includes.

Known issues.

  • The redaction rule is enforced for message by construction and for provider_code by its character set; a provider code made of a user's data in those characters (an implementation that passes an email's local part as a code) is still the implementation's defect, which the kits look for but cannot rule out.
  • The enumeration is shared: a code that is meaningless for one capability (insufficient_funds from a message sender) is never returned by it, but the type does not forbid it.

Status. New in 0.23.0. Experimental, with the contracts.
