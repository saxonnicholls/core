Detailed Description

snicholls::ml::token_trie: a tokenizer vocabulary as a trie over its pieces' bytes, held as the ids sorted by piece, so it is built by one sort (at compile time for a fixed vocabulary) and walked without allocation.

Overview. Every tokenizer asks its vocabulary two questions: is this byte string a token, and which tokens are prefixes of the text from here (Unigram's Viterbi lattice, WordPiece's longest match, RWKV's greedy match). A sorted array answers both. With the ids ordered by their pieces' bytes, the pieces sharing a prefix are one contiguous range, and extending the prefix by a byte narrows the range by two binary searches: that is a trie, walked one byte at a time (cursor, advance, at), with no nodes to build or store.

  • build_token_index(pieces, order, keep) fills order with the ids keep accepts, sorted by piece. It is constexpr, so static_token_trie<N> holds a fixed vocabulary's index computed by the compiler.
  • token_trie{pieces, order} is the view: find(bytes) (exact match, O(L log V)), longest_prefix(text), and the cursor walk.
  • token_kind is what a token is, numbered as GGUF stores it.

The pieces are the caller's: a span of std::string_view into a tokenizer file's string table, or a constexpr array of literals. Pieces are bytes, compared unsigned.

// A vocabulary the compiler sorts: ids are positions in the array
constexpr ml::static_token_trie<6> vocab{std::array<std::string_view, 6>{"<unk>", "un", "unaff", "able", "a", "unaffable"}};
static_assert(vocab.view().find("able") == 3 && vocab.view().find("abl") == ml::no_token);
// Every token that is a prefix of "unaffable!", by walking the trie one byte at a time
constexpr std::size_t prefixes()
{
const ml::token_trie t = vocab.view();
std::size_t found = 0;
auto c = t.root();
for (const char b : std::string_view("unaffable!"))
if (!t.advance(c, b))
break;
else if (t.at(c) != ml::no_token)
++found; // "un", "unaff", "unaffable"
return found;
}
static_assert(prefixes() == 3);

Relationships. The vocabulary behind ml/unigram.hpp, ml/wordpiece.hpp, ml/rwkv_tokenizer.hpp, and the token lookups of ml/sentencepiece.hpp and ml/bpe_merges.hpp (any callable will do there; this is the allocation-free one). containers/perfect_map.hpp is the faster exact lookup when only find is needed and the vocabulary is fixed. Group: snicholls-core.

Implementations. One. Against a node trie (llama.cpp's naive_trie, a std::map per node) it stores nothing but the 4-byte ids and costs a binary search per byte instead of a map lookup.

Guarantees. constexpr; noexcept except build_token_index, which only sorts. No allocation; the view does not own the pieces or the order, which must outlive it. Complexity: building O(V log V · L); find O(L log V); advance O(log V) per byte, shrinking as the range narrows. When pieces repeat, the largest id is the one found (llama.cpp's vocabulary map keeps the last).

Errors. build_token_index asserts order.size() >= pieces.size(); ids are std::uint32_t.

Performance. benchmarks/ml/token_trie_benchmark.cpp, about 13,000 pieces (Release, Apple clang 17, Xeon W-3245, 2026-11-19, one thread on a loaded machine (ratios held across runs)): the longest token at every byte of a text, 13 MiB/s against 40 MiB/s for a node trie of std::maps (llama.cpp's naive_trie); find, 11 million lookups/s against 31 million for std::unordered_map. The sorted array is about three times slower than either and stores 4 bytes per token instead of a node per byte; a caller that needs the speed and not the compile-time form puts a hash map behind the same lookup callable.

Tests and demos. tests/ml/token_trie_test.cpp (against a linear scan on random vocabularies, duplicates, the empty piece, bytes above 0x7F, a compile-time trie), demos/ml/token_trie_demo.cpp.

Dependencies. <array>, <cassert>, <cstddef>, <cstdint>, <span>, <string_view>.

Known issues. Each step of a walk is two binary searches over string views (two indirections a probe), which is what makes it slower than a node trie (see Performance).

Status. Experimental, new in 0.17.0.
