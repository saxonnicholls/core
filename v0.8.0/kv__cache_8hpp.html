Detailed Description

snicholls::ml::kv_cache_view and kv_cache: the keys and values of every layer and key-value head, laid out so one head's keys are contiguous, with a sliding window as a ring.

Overview. Decoding a token attends to the keys and values of every earlier position, so they are kept, per layer and per key-value head, in [layer][kv_head][slot][head_dim]: the keys one head reads are contiguous rows, which is what attend and attention_accumulator take. Position p is in slot p % capacity, so one layout serves both uses:

  • a capacity of the longest sequence: every position has its own slot (a flat cache);
  • a capacity of at least the sliding window: older slots are overwritten (a ring), and the keys a query may see are at most two contiguous runs, visited in position order.

kv_cache_view<C, T> works over two spans the caller owns (keys and values), sized by required_size; kv_cache<C, T, Layers, Capacity> owns fixed-size arrays and hands out a view.

paged_kv_cache_view<C, T, MaxPages> is the form for serving: a pool of fixed pages and a page table per sequence, so sequences that share a prefix share its pages, and kv_page_hash gives each page a content address (its tokens and the address of the page before), so a request can find the pages an earlier one already computed. A visible range is one run per page, still in position order, so a paged cache gives the flat cache's bits. The pool's allocation, sharing and eviction are the serving layer's, above core.

// One key-value head of 2 channels, a sliding window of 3: a ring of 3 slots is enough
constexpr ml::transformer_config c{.d_model = 2, .n_heads = 1, .n_kv_heads = 1, .head_dim = 2, .d_ff = 2, .window = 3};
std::vector<float> keys(ml::kv_cache_view<c>::required_size(1, 3)), values(keys.size());
const ml::kv_cache_view<c> cache(keys, values, 1, 3);
for (std::size_t pos = 0; pos < 5; ++pos) {
const std::array<float, 2> k{float(pos), float(pos)}, v{-float(pos), -float(pos)};
cache.append(0, pos, k, v); // position 3 overwrites slot 0, position 4 slot 1
}
// Position 4 sees positions 2, 3 and 4: slot 2, then slots 0 and 1
const ml::kv_runs<float> runs = cache.visible(0, 0, ml::attention_window(4, c.window));
// The same cache owning its storage, for a model small enough to hold
static ml::kv_cache<c, float, 1, 3> owned;
owned.view().append(0, 0, std::array<float, 2>{7, 7}, std::array<float, 2>{8, 8});

Relationships. ml/transformer_config.hpp, ml/attention.hpp (key_range, attention_window), ml/attention_layer.hpp (the user). Group: snicholls-core.

Implementations. The flat or ring layout, over the caller's memory or owned; the paged layout over the caller's pool.

Guarantees. constexpr, no allocation, O(kv_size) per append, O(1) to find the visible runs. A view does not own its spans and copying it shares them; the owning form builds its view per call, so a copy of it is a cache of its own. The cache records no length: the caller says which positions it appends and reads.

Errors. Preconditions, asserted: the spans have required_size(layers, capacity) elements; a layer is below layers; a visible range is at most capacity long and ends at or before the last appended position plus one.

Performance. O(kv_size) copies per token per layer; benchmarked through ml/transformer_block.hpp.

Tests and demos. tests/ml/kv_cache_test.cpp, demos/ml/kv_cache_demo.cpp.

Dependencies. <algorithm>, <array>, <cassert>, <concepts>, <cstddef>, <cstdint>, <span>, <type_traits>, hash/wyhash.hpp, ml/attention.hpp, ml/row.hpp, ml/transformer_config.hpp.

Known issues. A kv_cache of a real model is large (Llama 3 8B: 128 KB per position across its 32 layers in float): give it static storage, or use the view over memory of your own.

Status. Experimental, new in 0.8.0.

The content address of a page of tokens: a hash of its tokens and of the page before it, so equal addresses mean equal prefixes (up to a 64-bit collision; check the tokens on a hit).

A page's keys and values depend on every token before it, so a cache of pages is keyed by the whole prefix: the address of page i is kv_page_hash(address of page i - 1, its tokens), from kv_page_hash_root for the first. Two requests whose prompts start alike reach the same addresses and can share those pages. Machine-independent: the tokens are mixed as integers, never as bytes in memory.

Parameters
parentThe address of the page before, or kv_page_hash_root.
tokensThe page's tokens.
Returns
The address.
