Detailed Description

The linear-algebra interface: the linalg::backend concepts and the free functions that check extents and call a backend, resolved at compile time.

Overview. Callers write against one set of free functions - linalg::dot, gemm, lu_factor, cholesky_solve, symmetric_eigen, ... - and pass the backend as the first argument. A backend is any type whose members model the concepts below: core's reference_backend, or one from a companion library binding BLAS and LAPACK, Eigen or an accelerator. Everything is resolved at compile time: the free function is a template, the backend's member is called directly and inlines, and there is no virtual call, function pointer or type erasure anywhere, so a hot loop over a million small systems costs what the hand-written loop costs.

// Generic code: solve A x = b with whichever backend it is given. Every call is resolved at compile time.
template <typename Backend>
double solve_and_check(const Backend& backend)
{
std::array<double, 9> a{4, -2, 1, -2, 4, -2, 1, -2, 4}; // symmetric positive definite
std::array<double, 3> b{11, -16, 17}; // A (1, -2, 3)
const la::matrix_view<double, la::layout_right> A(a.data(), {3, 3});
const auto x = la::as_vector(std::span<double>(b));
if (!la::cholesky_factor(backend, A) || !la::cholesky_solve(backend, A, x))
return -1.0;
return std::abs(b[0] - 1) + std::abs(b[1] + 2) + std::abs(b[2] - 3); // the error
}

The free functions take any md_span layout (row-major, column-major, strided) and any right-hand side as a vector or a matrix, check that the extents fit together (error::dimension_mismatch otherwise), and hand the backend the canonical views: matrix_view<T> / vector_view<T> (strided), const for inputs. A backend therefore implements one member per operation and never sees a layout it was not written for.

Choosing a backend at run time. There is deliberately no run-time adapter. A program that picks its backend at run time (a GPU backend if a device is present, otherwise BLAS) branches once, at the top, between two instantiations of its own generic code, and each instantiation is resolved at compile time:

// Choosing a backend at run time: branch once, at the top, between two instantiations of the generic code.
// Inside each branch every call is still resolved at compile time; nothing is erased or virtual.
double run(bool use_reference)
{
if (use_reference)
return solve_and_check(la::reference);
return solve_and_check(counting_backend{});
}

The contract a backend implements (each member const; T is float, double or another scalar; M<T> is matrix_view<T>, V<T> is vector_view<T>, R is result<void, error>). Extents are checked before a member is called, so a member may assume them.

backend<B, T> is all four. Storage follows LAPACK so that lu_log_det, cholesky_log_det, ldlt_log_det and the conformance suite read any backend's factors: LU as getrf (0-based pivots), Cholesky and LDLT in the lower triangle, QR as geqrf (R on and above the diagonal). log_dets and lu_inverse are written once, here, on top of those members.

Relationships. linalg/types.hpp (the views and codes), linalg/reference.hpp (core's backend), linalg/batched.hpp (batches), result.hpp. The conformance suite every backend registers in is tests/support/snicholls/core/conformance/linalg.hpp (CMake target snicholls::core_conformance). Group: snicholls-core.

Implementations / variants. In core: reference_backend (standard library only, naive, constexpr, deterministic). Third-party backends live in companion libraries, never in core.

Guarantees. The free functions add a few comparisons of extents and nothing else; they are constexpr, not declared noexcept, and throw only what the backend's member throws (the reference backend's members are noexcept for float and double). A backend's own guarantees (determinism, threads, allocation) are its own: the reference backend's are in linalg/reference.hpp.

Errors. error::dimension_mismatch from the extent checks and error::aliased when an output view starts where an input does (gemm(.., a, .., a), symmetric_eigen(a, w, a)), both before the backend is called and with every argument unchanged. The span outputs (pivots, tau, w, s) are checked the same way. Other overlap (one view inside another, interleaved strides) is not detected: every function's \pre forbids it; otherwise what the member returns (see each function). A backend type that lacks a member is a compile error naming the member it lacks (a static_assert with a snicholls::linalg:: message).

Performance. The concept path compiles to the backend's member called directly. Every member of the reference backend's concepts is benchmarked through these functions against the same algorithm written by hand, after a bit-for-bit fairness check; lu_inverse (one lu_solve) and the three log_dets (one pass over a diagonal) are not benchmarked: benchmarks/linalg/reference_benchmark.cpp and batched_benchmark.cpp; the figures (Release, AppleClang 17, Xeon W-3245, macOS 26, 2026-11-11, on a shared machine with load average 7 to 10) are in linalg/reference.hpp, linalg/batched.hpp and BENCHMARKS.md.

Tests and demos. tests/linalg/backend_test.cpp (the concepts, a backend missing an operation, the extent checks, a recording backend), the compile-fail case tests/compile_fail/linalg_backend_missing_member.cpp, demos/linalg/backend_demo.cpp.

Dependencies. <concepts>, <cstddef>, <limits>, <span>, <type_traits>, result.hpp, linalg/types.hpp, linalg/batched.hpp.

Known issues. Complex numbers are not supported yet (no conjugate transposes).

Status. Experimental, new in 0.6.0.
