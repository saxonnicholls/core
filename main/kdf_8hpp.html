Detailed Description

HKDF (RFC 5869) and PBKDF2-HMAC (RFC 8018) over any hash in core, writing into the caller's memory.

Overview. Two key derivation functions, for two different jobs.

  • HKDF turns key material that is already strong but not uniform (a Diffie-Hellman shared secret, a master key) into as many independent keys as a protocol needs: hkdf_extract concentrates the material into a pseudorandom key, hkdf_expand stretches that into output bound to an info label, and hkdf does both. TLS 1.3, Signal, Noise, HPKE and MLS use it. It is fast: never use it on a password.
  • PBKDF2-HMAC stretches a password by iterating HMAC, so that each guess costs an attacker the same iterations HMACs it costs you. BIP-39 seeds are PBKDF2-HMAC-SHA512 with 2048 iterations; OWASP's 2023 guidance is 600,000 iterations of SHA-256 or 210,000 of SHA-512. Prefer scrypt (hash/scrypt.hpp) for a new password store, since PBKDF2 costs a GPU little memory.
// HKDF: one shared secret, independent keys bound to their purpose by `info`
struct keys
{
std::array<std::byte, 32> client_to_server, server_to_client;
};
keys split(const std::string& shared_secret, const std::string& handshake_salt)
{
keys k{};
const auto prk = snicholls::hkdf_extract<snicholls::sha256>(handshake_salt, shared_secret);
(void)snicholls::hkdf_expand<snicholls::sha256>(prk, "c2s key", k.client_to_server); // 32 <= 255 * 32: cannot fail
(void)snicholls::hkdf_expand<snicholls::sha256>(prk, "s2c key", k.server_to_client);
return k;
}
// PBKDF2: BIP-39's seed is PBKDF2-HMAC-SHA512(mnemonic, "mnemonic" + passphrase, 2048 iterations, 64 bytes)
snicholls::result<snicholls::digest<64>, snicholls::kdf_error> bip39_seed(const std::string& mnemonic, const std::string& passphrase)
{
return snicholls::pbkdf2_hmac<snicholls::sha512, 64>(mnemonic, "mnemonic" + passphrase, 2048);
}

Output goes into a span the caller owns, so nothing allocates; the <H, L> forms return a digest<L> and are usable in a constant expression. Expected failures (an output too long for the function, zero iterations) are a result<void, kdf_error>, never an exception.

Relationships. hmac<H> (hash/hmac.hpp); hash_function and digest<N> (hash/digest.hpp); secure_wipe (hash/secure.hpp); scrypt, which uses pbkdf2_hmac<sha256>; blake3::derive_key (hash/blake3.hpp), a faster key derivation where HKDF is not required. Group: snicholls-core.

Guarantees. Every function is constexpr and noexcept; no allocation. Intermediate blocks are wiped with secure_wipe. On an error nothing is written. Complexity: HKDF, ceil(L / HashLen) HMACs; PBKDF2, ceil(L / HashLen) * iterations HMACs, two compressions each.

Errors. kdf_error::output_too_long when HKDF is asked for more than 255 * HashLen bytes or PBKDF2 for more than (2^32 - 1) * HashLen; kdf_error::empty_output for an empty output span; and from PBKDF2, kdf_error::zero_iterations.

Examples. Above; demos/hash/kdf_demo.cpp.

Performance. benchmarks/hash/kdf_benchmark.cpp: PBKDF2-HMAC-SHA256 and -SHA512 against a hand-written loop and OpenSSL's PKCS5_PBKDF2_HMAC (when installed), after a fairness check. Release, Apple clang 17, Xeon W-3245, 2026-11-20, 1,000 iterations, 64 bytes: SHA-256 core 1.13 ms, hand 1.13 ms, OpenSSL 0.80 ms; SHA-512 core 0.79 ms, hand 0.74 ms, OpenSSL 0.55 ms (OpenSSL's SHA-2 is faster, see hash/sha2.hpp).

Tests and demos. tests/hash/kdf_test.cpp (RFC 5869's test cases 1 to 7, RFC 6070's PBKDF2-HMAC-SHA1 vectors, RFC 7914's PBKDF2-HMAC-SHA256 vectors, Python's hashlib.pbkdf2_hmac on random inputs, the BIP-39 test seed, errors), demos/hash/kdf_demo.cpp.

Dependencies. <array>, <cstddef>, <cstdint>, <span>, hash/hmac.hpp, result.hpp (larger than it looks: about 2,500 lines).

Known issues. RFC 6070's 16,777,216-iteration vector is run by the tests only in Release builds.

Status. New in 0.17.0. Experimental.
