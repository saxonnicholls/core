Detailed Description

snicholls::onramp_provider_interface: the pure virtual twin of onramp_provider, and the adapters both ways.

Overview. When the venue is chosen by configuration, code holds a onramp_provider_interface&. Its pure virtual functions (assets, quote, buy, order_status, withdraw, withdrawal_status, balances, statement) are the operations of the concept onramp_provider (concepts/onramp_provider.hpp, where the contract and its value types are documented), so the interface models the concept itself. onramp_provider_adapter<O> puts any model behind the interface, owning it (O) or referring to it (O&); onramp_provider_ref is a copyable, non-owning handle on the interface that models the concept.

onramp_provider_adapter owned{make_venue()};
onramp_provider_interface& chosen = owned;
onramp_provider_ref handle{chosen};
const auto q = handle.quote({usdc, aud, *parse_money(aud, "15.30")});

Relationships. concepts/onramp_provider.hpp, interfaces/onramp_provider_reference.hpp, interfaces/onramp_provider_conformance.hpp. Group: snicholls-core.

Implementations / variants. onramp_provider_adapter<O> over any model; an implementation above core may derive from the interface directly.

Guarantees. The adapters add one virtual call and nothing else; thread safety and exception safety are the wrapped implementation's.

Errors. As the contract.

Performance. One virtual call; not benchmarked (a venue is I/O bound).

Tests and demos. tests/interfaces/onramp_provider_test.cpp (the kit through every form, the adapters forward), demos/interfaces/onramp_provider_demo.cpp.

Dependencies. <type_traits>, <utility>, concepts/onramp_provider.hpp.

Known issues. None.

Status. New in 0.23.0. Experimental until two real implementations pass the kit.
