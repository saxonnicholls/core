Detailed Description

template<class T, class Index = std::uint32_t>
class snicholls::containers::index_pool< T, Index >

A pool of T slots addressed by Index from the start of a caller's region, with a free list of indices.

Overview

object_pool hands out pointers, which mean nothing once the memory is mapped at another address. index_pool hands out indices: slot i is at a fixed offset from the region's start, the free list is threaded through freed slots as indices, and the pool's counters live in the first bytes of the region itself. So the region can be a memory-mapped file that is closed and reopened elsewhere, or a buffer that grows by being copied: call rebase with the new span and every index still names the same object. Indices are 32 bits by default, half the size of a pointer, which also makes them the cheaper link in structures inside the region.

Use it for many fixed-size records that must persist, move or be shared between processes. Not for types with pointers, virtual functions or owned resources (T must be trivially copyable), and not when addresses suffice: object_pool is simpler and does not need a region.

Region layout, in native byte order: 

[ state: 64 bytes, rounded up to region_alignment ][ slot 0 ][ slot 1 ] ... [ slot capacity()-1 ]

The state holds a magic number, the slot size and index width it was formatted for, the high-water mark, the head of the free list and the live count. Slots past the high-water mark have never been used.

Relationships
  • object_pool, the pointer-addressed pool on chunks from a std::pmr::memory_resource.
  • mapped_header (containers/mapped_header.hpp), the checked file header to put in front of a persisted region.
  • ts-moveables' mapped storage, which keeps an index_pool in a memory-mapped file.
  • Module: snicholls-core.
Implementations and variants

None: a single implementation, over Index = std::uint32_t (default) or std::uint64_t.

Guarantees and contracts
  • Thread safety: none internal; one writer. Readers of slots that no one destroys may run concurrently.
  • Exception safety: nothing throws: every operation is noexcept, and refusals are result values.
  • Complexity: allocate / create / destroy / access O(1); format O(1) (slots are not touched); attach and rebase O(1) (the free list is not walked).
  • Ownership and lifetime: the caller owns the region; the pool is a view of it, trivially copyable. The region holds the pool's whole state, so two index_pool objects over one region are the same pool.
  • Invariants: live() <= high_water() <= capacity(); the free list holds exactly high_water() - live() indices, each below high_water().
Errors

format, attach and rebase return misaligned, too_small, not_formatted, layout_mismatch or corrupt (see index_pool_error); allocate and create return full when every slot is in use.

Examples
auto made = snicholls::containers::index_pool<order>::format(small.span()); // an empty pool in the region
if (made.is_err()) return 1;
auto pool = *made;
std::uint32_t a = *pool.create(order{1, 100, 990});
std::uint32_t b = *pool.create(order{2, 200, 991});
pool.destroy(a); // index 0 goes on the free list ...
std::uint32_t c = *pool.create(order{3, 300, 992}); // ... and is reused first

Growing the region by copying it, and carrying on with the same indices:

buffer big(pool_t::bytes_for(1024));
std::memcpy(big.span().data(), small.span().data(), small.span().size()); // grow: copy, or remap a file
if (pool.rebase(big.span()).is_err()) return 1;
std::uint32_t d = *pool.create(order{6, 600, 995});
Performance

benchmarks/containers/index_pool_benchmark.cpp compares it like for like with a hand-written index free list over a std::vector and with object_pool, after a fairness check: 4,096 creates, 2,048 destroys and re-creates, every record read, everything destroyed. Release, Apple Clang 17, Intel Xeon W-3245 (macOS 26), 2026-11-12, median of 5 on a loaded machine: index_pool 23.7 µs (173 M items/s), the vector free list 32.5 µs, object_pool 37.0 µs. The pool wins because its free list lives in the freed slots, not in a second vector.

Known issues and gotchas
  • A double destroy(i) is not detected and links i into the free list twice, as object_pool does; and attach trusts the free list it finds (it checks the counters, not each link), so a region written by a different program must be trusted, or validated by its owner (mapped_header's checksum covers only the header).
  • The layout is native: a region is readable only by a build with the same T layout, index width and byte order. layout_mismatch catches a different slot size or index width, not a reordered T.
  • Slot memory past high_water() is never written by format or rebase, so a sparse file stays sparse.
  • allocate returns a slot whose bytes are whatever was there; create writes a value.
