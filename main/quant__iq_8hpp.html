Detailed Description

snicholls::ml ggml's IQ quantisation family, byte for byte: IQ1_S, IQ1_M, IQ2_XXS, IQ2_XS, IQ2_S, IQ3_XXS, IQ3_S (lattice codebooks with sign bits), IQ4_NL and IQ4_XS (non-linear 4-bit values), with ggml's importance-weighted quantisers, the decoders and the integer dot products with Q8_K (Q8_0 for IQ4_NL), all constexpr.

Overview. The IQ formats quantise a group of 8 (IQ1, IQ2) or 4 (IQ3) magnitudes to the index of the nearest point of a fixed grid (ml/quant_iq_grids.hpp), the signs to 7 or 8 bits, and a sub-block scale to 3 or 4 bits; IQ4 maps each weight to one of 16 non-linear values. They are what llama.cpp ships below 4 bits per weight:

Block Elements Bytes Bits per weight Groups Importance matrix
block_iq1_s 256 50 1.5625 8 of the 2048-point ternary grid, shift ±1/8 per 32 required
block_iq1_m 256 56 1.75 as IQ1_S, a shift per 8 and a scale per 16 optional
block_iq2_xxs 256 66 2.0625 8 of 256 points, 7 sign bits (even parity) required
block_iq2_xs 256 74 2.3125 8 of 512 points, a scale per 16 required
block_iq2_s 256 82 2.5625 8 of 1024 points, 8 sign bits optional
block_iq3_xxs 256 98 3.0625 4 of 256 points, 7 sign bits per 8 optional
block_iq3_s 256 110 3.4375 4 of 512 points, 8 sign bits optional
block_iq4_nl 32 18 4.5 16 non-linear values optional
block_iq4_xs 256 136 4.25 as IQ4_NL, 6-bit scales per 32 optional

Each follows ml/quantize.hpp's contract: quantize_row(x, importance, blocks) is ggml's quantize_<type>(x, blocks, 1, n, importance) (an empty importance is ggml's null; IQ1_S, IQ2_XXS and IQ2_XS, which ggml refuses to quantise without one, assert it), dequantize_row is dequantize_row_<type>, and dot is ggml_vec_dot_<type>_q8_K_generic. quantize_row_reference is IQ4_NL's quantize_row_iq4_nl_ref (no scale search, as ggml's CPU backend quantises IQ4_NL activations and caches).

// Weights to an IQ format, minimising the importance-weighted error as llama-quantize does
std::vector<B> wq(n / B::elements);
ml::quantize(w, importance, std::span<B>(wq));
// Activations to the format's partner (Q8_K, or Q8_0 for IQ4_NL), then the integer dot product
std::vector<A> aq(n / A::elements);
ml::quantize(a, std::span<A>(aq));
const float d = ml::dot(std::span<const B>(wq), std::span<const A>(aq));
// And back to floats
std::vector<float> back(n);
ml::dequantize(std::span<const B>(wq), back);

Relationships. ml/quantize.hpp (the type ids, block_q8_k, block_q8_0, the scale searches make_qp_quants, nearest_int), ml/quant_iq_grids.hpp (the codebooks). block_iq4_nl is a quant_block, so ml/linear.hpp's quantized_weights takes it. Group: snicholls-core.

Implementations. ggml keeps, per grid, a table of each off-grid point's nearest grid points (kneighbors, built by iq2xs_init_impl / iq3xs_init_impl over 43,692 and 4,096 points). Core computes a point's neighbours when the quantiser asks for them: every grid point's distance, then the points of the nwant smallest distances in ggml's sorted order (distance, then index), so the choice is ggml's to the bit and the function stays constexpr without a 100 KB table. That costs one pass over the grid per off-grid group.

Guarantees. constexpr (quantising a whole IQ1, IQ2 or IQ3 block at compile time takes more than Clang's default 1,048,576 evaluation steps, -fconstexpr-steps; GCC's limit is far higher), no allocation (the largest buffer is 8 KB on the stack, IQ1's distances), linear in the row. The blocks are trivially copyable with ggml's sizes (static_asserted). Bytes, dequantised floats and dot products equal ggml's on every row kind of the committed fixture (tests/fixtures/ml/quant_iq_fixture.txt, from scripts/generate_quant_iq_fixture.cpp built against ggml), except where noted under Known issues. Each multiplication and addition is its own statement, so no FMA is formed (compile GCC with -ffp-contract=off).

Errors. Preconditions, asserted: the row has elements · blocks.size() numbers; importance is empty or as long as the row (and not empty for IQ1_S, IQ2_XXS, IQ2_XS); dot products' rows have the same number of blocks.

Performance. Dot products and dequantisation against ggml's scalar loops written out by hand (benchmarks/ml/quant_iq_benchmark.cpp); see BENCHMARKS.md. Quantisation is a model-conversion step: the on-demand neighbour search makes it slower than ggml's table lookups (not benchmarked against them).

Tests and demos. tests/ml/quant_iq_test.cpp, demos/ml/quant_iq_demo.cpp.

Dependencies. <array>, <cassert>, <cstddef>, <cstdint>, <limits>, <span>, ml/quantize.hpp, ml/quant_iq_grids.hpp.

Known issues. IQ1_S and IQ1_M sort each block's weights with C's qsort on the value alone, so ggml's order of equal weights is its C library's; core sorts stably (equal values in their original order). Where a block has equal weights the bytes can differ from ggml's on some C libraries; the committed fixture (macOS) agrees on every row kind except where a tie changes the prefix sums (listed in the test). With a NaN in a row ggml aborts for IQ1_M, IQ2_XS, IQ2_S, IQ3_XXS and IQ3_S (its "point not on grid" assertion) and core asserts likewise; IQ1_S, IQ2_XXS and the IQ4 formats give ggml's bytes. Where ggml's IQ1 neighbour search finds no candidate (only with infinities) its fallback reads past the group; core searches the whole grid instead. IQ4_NL's quantize_row_reference leaves a block of zeros with the codes of the block before it, as ggml does (the first block's codes are then 0; ggml's are uninitialised memory).

Status. Experimental, new in 0.17.0.
