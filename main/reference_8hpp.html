Detailed Description

linalg::reference_backend: the standard-library-only backend, naive and correct, that every other backend is checked beside.

Overview. Textbook algorithms written once, generic in the number type, over strided views: the BLAS operations as loops, LU with partial pivoting, Cholesky and LDLT (Crout order), Householder QR, the cyclic Jacobi method for the symmetric eigenproblem and the one-sided (Hestenes) Jacobi SVD. It models linalg::backend, so it is what linalg::lu_factor(linalg::reference, a, pivots) and the batched solves run when no other backend is chosen, and it is the baseline of the conformance suite (tests/support/snicholls/core/conformance/linalg.hpp). Use it for small systems (the batched solves of sizes up to about a hundred are its strength), on a device, at compile time, or where a dependency is not allowed; use a tuned backend from a companion library for large dense matrices.

// The reference backend is constexpr: the compiler can solve a small system and check it.
constexpr std::array<double, 3> solve_at_compile_time()
{
std::array<double, 9> a{2, 1, 0, 1, 3, 1, 0, 1, 4};
std::array<double, 3> b{4, 10, 14}; // A (1, 2, 3)
std::array<la::pivot_index, 3> p{};
const la::matrix_view<double, la::layout_right> A(a.data(), {3, 3});
if (!la::lu_factor(la::reference, A, std::span<la::pivot_index>(p)) ||
!la::lu_solve(la::reference, A, std::span<const la::pivot_index>(p), la::as_vector(std::span<double>(b))))
return {};
return b;
}
static_assert(solve_at_compile_time()[2] > 2.999999 && solve_at_compile_time()[2] < 3.000001);
// At run time: the principal components of a 3 x 3 covariance matrix.
std::array<double, 3> principal_variances()
{
std::array<double, 9> cov{4.0, 1.2, 0.4, 1.2, 2.0, 0.3, 0.4, 0.3, 1.0};
std::array<double, 9> loadings{};
std::array<double, 3> variances{};
const auto r = la::symmetric_eigen(la::reference, la::matrix_view<double, la::layout_right>(cov.data(), {3, 3}),
std::span<double>(variances), la::matrix_view<double, la::layout_right>(loadings.data(), {3, 3}));
return r ? variances : std::array<double, 3>{};
}

Relationships. Models linalg::backend (linalg/backend.hpp); its batched members run per system through linalg/batched.hpp's for_each_system. Group: snicholls-core.

Implementations / variants. One implementation per operation. Each member looks at its views' strides once per call (once per system in a batch) and runs the same kernel on the accessor the compiler optimises best: a packed square matrix (one run-time number for the order and the row stride, as a hand-written kernel has), rows or columns with unit stride and a leading dimension, or any strides. A right-hand side prefers unit stride down its columns, which the substitutions walk. A contiguous matrix therefore gets the code a hand-written loop gets.

Guarantees. Every member is constexpr, and noexcept when T's arithmetic is (float, double; not an allocating multiprecision type, whose bad_alloc propagates), except the batched ones, which call the caller's executor; none allocates or uses workspace beyond its arguments; loops are bounded by the extents and, for the iterative decompositions, by max_sweeps. The backend is a trivially copyable type holding one double (relative_tolerance). Determinism: every sum runs in ascending index order in the argument's own type, and nothing inside an operation runs in parallel, so a result is bit-for-bit the same on every call and for every executor of a batch. Across compilers or flags it is the same only if floating-point contraction (-ffp-contract) is.

Errors. As linalg/backend.hpp documents for each operation: singular when a pivot magnitude is at or below pivot_tolerance (a NaN pivot counts as zero), not_positive_definite when a Cholesky diagonal is, did_not_converge when Jacobi uses max_sweeps or its input holds a NaN or an infinity (the Jacobi methods scale by the largest element first, so no sum of squares overflows or underflows). A triangular solve reports singular only for an exact zero on the diagonal, as LAPACK's does. On an error the matrix holds a partial factorisation and must not be used.

Known issues. Naive by design: no blocking, no vectorised reductions (they would change the order of the sums). LDLT is unpivoted. Its accuracy degrades with the element growth a small leading pivot causes (about epsilon / |d_min| relative error, e.g. 2e-10 for [[1e-6, 1, 0], [1, 0, 1], [0, 1, 1]], where LU gives 4e-16), so it measures the growth and reports singular above ldlt_growth_limit(n), and for an exactly zero pivot; solve those with LU. Positive-definite matrices (growth at most 1) and bordered systems (growth about 2 k at most, ldlt_growth_limit) stay far below the limit. The growth check guards accuracy, not singularity, so it applies whatever relative_tolerance is. The SVD's columns of U for zero singular values are zero, not completed to an orthonormal basis. symmetric_eigen and cholesky_factor read only the lower triangle. QR scales tau and v, but the reflector's inner product w = b_k + sum v_i b_i is not: inputs whose column sums exceed the range (a tall column of values near the largest finite one) overflow there. An eigenvalue or singular value beyond the type's range comes back as infinity, the correctly rounded value, with success: [[1e308, 1e308], [1e308, 1e308]] has eigenvalues 0 and 2e308, returned as {0, inf}.

Status. Experimental, new in 0.6.0.
