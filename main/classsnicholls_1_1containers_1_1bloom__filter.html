Detailed Description

A fixed-size probabilistic set: "definitely not present" in O(k), or "maybe present".

Overview

A million watched addresses and a stream of events, nearly all of which are not for us: the hot path must reject a non-member in constant time with no map lookup. A Bloom filter sets k bits per key in a bit array of m bits; a query reads the same k bits and answers "no" if any is clear, which is never wrong, or "maybe" if all are set, which is wrong with a probability the sizing chose. A "maybe" falls through to the authoritative container; a "no" costs k hashes and k bit reads.

// The authoritative map: 100,000 watched addresses and who owns each.
std::unordered_map<std::string, int> owners;
for (int i = 0; i < 100'000; ++i)
owners.emplace("0x" + std::to_string(i * 2654435761u), i);
// The filter in front of it, sized for those keys at a 0.5% false-positive rate.
snicholls::containers::bloom_filter watched(owners.size(), 0.005);
for (const auto& [address, owner] : owners)
watched.add(address);
std::printf(" %zu addresses, %zu KB, %u hashes per key\n", owners.size(), watched.memory_bytes() / 1024, watched.hashes());
// A stream of events, half of them ours: "no" is final, "maybe" asks the map.
std::size_t ours = 0, rejected_by_filter = 0, rejected_by_map = 0;
for (int i = 0; i < 200'000; ++i) {
const bool watched_address = i < 100'000;
const std::string address = (watched_address ? "0x" : "0y") + std::to_string(i * 2654435761u);
if (!watched.maybe_contains(address)) {
++rejected_by_filter; // certain, and no lookup
continue;
}
if (owners.contains(address))
++ours;
else
++rejected_by_map; // a false positive: one wasted lookup
}

Sizing: bloom_filter(n, p) picks m and k for n keys at false-positive rate p (bloom_sizing); 1,000,000 keys at 0.5% is 1.7 MB and 8 hashes. The k positions come from two 64-bit values by double hashing, h1 + i * h2, where h1 is wyhash of the key and h2 is splitmix64(h1) made odd, so one hash of the key serves every bit.

Implementations and variants

One class; the words are plain std::uint64_t. A lock-free read side (bits only ever set, never cleared, so a reader racing a writer of another key sees no false negative) is a wrapper over words() with atomic loads, in a library that has threads.

Guarantees and contracts
  • No false negatives: a key that was added is always "maybe present".
  • maybe_contains is const, noexcept, O(k), allocation-free; add is noexcept once constructed. Not thread-safe: synchronise add against readers externally.
  • Memory: bits() / 8 bytes, allocated once by the constructor; clear keeps it.
  • merge requires the same bits() and hashes() (asserted); the result is the union.
  • estimated_false_positive_rate() is (1 - e^(-k n / m))^k for the count() added so far.
Errors

std::bad_alloc from the constructor only.

Performance

Benchmarked in benchmarks/containers/bloom_filter_benchmark.cpp against the same filter written by hand over a std::vector<std::uint64_t> with the same hashes, on 4,096 queries half of which are members, after a fairness check; a std::unordered_set<std::string> lookup runs beside them for scale. Release, Apple clang 17, Xeon W-3245, 2026-11-06, 65,536 keys at 1%: 39.5 ns per query through the class, 40.0 ns by hand, 54 ns for the exact set. Zero overhead; the cost is the hash and seven dependent bit reads.

Dependencies

CMake target snicholls::core; standard library only, plus hash/wyhash.hpp.

Known issues and gotchas

A filter is sized for n keys; adding many more raises the false-positive rate past p (watch estimated_false_positive_rate()). Keys are bytes: the same text as a std::string_view and as a span of its bytes is the same key, but "1" and the integer 1 are not.
