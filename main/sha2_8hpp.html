Detailed Description

SHA-224, SHA-256, SHA-384, SHA-512, SHA-512/224 and SHA-512/256 (FIPS 180-4), usable at compile time.

Overview. The SHA-2 family, each as a class with an incremental interface (update any number of times, then finish) and a one-shot hash. Every function is constexpr, so a digest of a short input is a constant the compiler computes and a static_assert can check; at run time the same code runs, with word loads the compiler fuses into one load and a byte swap. Input is any hash_input (text, bytes, a digest); output a digest<N>.

// A content address the compiler computes: a build can refuse a payload whose hash changed
constexpr auto schema_id = snicholls::sha256::hash("schema v3: id u64, price i64, qty i64");
static_assert(schema_id.first<4>().hex().view() == "13f63a67");
// Data that arrives in pieces is hashed as it arrives: the digest is the one-shot digest
std::string checksum(const std::string& header, const std::string& body)
{
snicholls::sha256 h;
h.update(header).update(body);
return std::string(h.finish().hex().view());
}

Use SHA-256 for content addresses, file and model checksums, Bitcoin's double hash and anything a protocol names; SHA-512 where a protocol names it (Ed25519, BIP-32 and BIP-39 through HMAC-SHA512), and on 64-bit hosts where its 128-byte block makes it faster than SHA-256 per byte. SHA-512/256 is SHA-512's speed with a 32-byte digest and no length extension. For a password use pbkdf2_hmac or scrypt (hash/kdf.hpp, hash/scrypt.hpp), never a bare hash; for a message authentication code, hmac<sha256> (hash/hmac.hpp).

Relationships. digest<N> and hash_input (hash/digest.hpp); hmac, hkdf_*, pbkdf2_hmac, scrypt build on these; sha1 (hash/sha1.hpp) and ripemd160 share the Merkle-Damgard engine (detail/hash_engine.hpp). Group: snicholls-core.

Implementations / variants. sha224 and sha256 share the 32-bit compression (64-byte blocks); sha384, sha512, sha512_224 and sha512_256 share the 64-bit compression (128-byte blocks). Each variant is the shared compression with its own initial value and a truncated output, as FIPS 180-4 defines it.

Guarantees. Every member is constexpr and noexcept; no allocation, no I/O, no global state; a hasher is a trivially copyable value (a copy forks the computation, which hmac uses). Not thread-safe to share one object between threads; distinct objects are independent. Complexity: one compression per block. After finish the object must not be used again except by assigning a fresh one.

Errors. None. Input longer than 2^61 bytes (the length field's limit for SHA-256) is not supported.

Examples. Above; demos/hash/sha2_demo.cpp.

Performance. benchmarks/hash/sha2_benchmark.cpp, against a hand-written loop with memcpy loads and OpenSSL's EVP interface when it is installed, after a fairness check that every digest agrees. Release, Apple clang 17, Xeon W-3245 (a shared machine), 2026-11-20, 16 KiB / 64-byte messages: SHA-256 core 239 / 119 MB/s, the hand loop 236 / 114, OpenSSL 514 / 101; SHA-512 core 374 / 165, hand 340 / 173, OpenSSL 760 / 116. OpenSSL's lead on long inputs is its SIMD schedule and, on CPUs that have them, the SHA instructions, which core cannot use (no platform headers); on short messages its per-call cost dominates.

Tests and demos. tests/hash/sha2_test.cpp (the FIPS 180-4 examples, NIST's byte-oriented short-message and Monte Carlo vectors from tests/fixtures/hash/, Python's hashlib on random lengths, every split of an input, compile-time digests), demos/hash/sha2_demo.cpp.

Dependencies. <array>, <cstddef>, <cstdint>, hash/digest.hpp, detail/hash_engine.hpp.

Known issues. SHA-256 and SHA-512 admit length extension: H(secret || message) is not a MAC; use hmac. Hashing a long input in a constant expression can reach the compiler's evaluation limit (Clang's -fconstexpr-steps, GCC's -fconstexpr-ops-limit): a few kilobytes is fine.

Status. New in 0.17.0. Experimental.
