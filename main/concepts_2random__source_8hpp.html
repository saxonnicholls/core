Detailed Description

snicholls::random_source_like: a source of cryptographically secure random bytes, which fails closed.

Overview. The contract for random bytes that must be unpredictable: keys, nonces, salts, session tokens, UUID v4 and v7's random bits. A source answers fill(data, size), writing exactly size bytes, and returns std::errc{} (zero: success); or it returns an error (random_failed(e)) and promises nothing about data. The result is std::errc, a literal type, so a source can be constexpr: test_random_source is, and keys, nonces and UUIDs drawn from it can be built and checked at compile time. It fails closed: a source that is unavailable or not yet seeded reports an error, and never falls back to a non-cryptographic generator. Core does no I/O, so it defines the contract and a test double only; the real source is the operating system's generator, implemented in ts-moveables (getrandom, getentropy, arc4random_buf, BCryptGenRandom). crypto, which pins only core, and core's own uuid generator take randomness through this contract, so neither depends on ts-moveables.

This is the concept half of a pair; the virtual twin is snicholls::random_source_interface (interfaces/random_source.hpp). Use stats::wyrand for simulation and Monte Carlo, never this; use this for secrets, never stats::wyrand or std::mt19937.

// A 128-bit session token from any random source; the caller's failure is ours, never a weaker fallback
template <typename Source>
std::errc session_token(Source& source, std::array<std::byte, 16>& token) noexcept
{
static_assert(snicholls::is_random_source_like_v<Source>, "a cryptographic random source");
return source.fill(token.data(), token.size());
}

Known issues. fill takes a pointer and a size rather than std::span, which is C++20. A platform's own error (a Windows status, an errno) is mapped by the implementation to the nearest std::errc.
