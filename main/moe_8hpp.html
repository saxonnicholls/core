Detailed Description

snicholls::ml mixture of experts for training: routing with a selection bias, the expert permutation, gather and combine, the grouped products and the experts' MLPs, the balance losses and the bias rule, load statistics, and the layer moe_forward / moe_backward over a batch of rows.

Overview. A mixture-of-experts (MoE) MLP replaces a transformer's one dense MLP by E smaller ones, the routed experts, of which each token uses K, plus optionally shared experts every token uses. A router (a linear map to E logits) chooses each token's experts and their weights; the token's output is the weighted sum of its experts' outputs. The parameters grow with E while the work per token grows only with K. The configuration's expert fields (transformer_config::experts, top_k, shared_experts, expert_d_ff, scoring, route_scale and the balance settings) choose among the published designs:

  • Switch Transformer (Fedus, Zoph and Shazeer, 2021) and OLMoE (Muennighoff et al., 2024): moe_scoring::softmax, a softmax over every expert, the chosen probabilities as weights, and the auxiliary balance loss alpha · E · sum_e f_e P_e.
  • Mixtral (Jiang et al., 2024): moe_scoring::softmax_top_k, the K largest logits, a softmax over those. This is moe_gate (ml/mlp.hpp) row by row, to the bit.
  • DeepSeekMoE (Dai et al., 2024) and DeepSeek-V3 (DeepSeek-AI, 2024): fine-grained experts (many, narrow), shared experts, moe_scoring::sigmoid (a sigmoid per expert, the chosen ones normalised, times route_scale), and auxiliary-loss-free balancing: a per-expert bias added to the scores for the choice only, never entering the weights, moved after each step by bias_e += gamma · sign(mean load - load_e) (moe_update_bias), with an optional small sequence-wise balance loss (moe_balance_loss with one sequence per group of rows).
  • ST-MoE (Zoph et al., 2022): the router z-loss beta · mean_t logsumexp(z_t)² (moe_z_loss), which keeps the logits small.

The steps. Every step is a free function taking the backend first, over rows laid end to end (TRAINING.md T9 and T10): core's overloads run on the host and define the result; a device library overloads each for its own backend type and the layer runs where its data lives.

  1. moe_route_rows: the router logits [rows x E] to each row's K experts (std::uint32_t, slot order: best first, ties to the lower expert) and weights; moe_route_rows_backward takes the weights' gradient back to the logits.
  2. moe_count_rows (a histogram of the rows · K choices), moe_offsets (its exclusive prefix sum, E + 1) and moe_permutation: the stable order of the (row, slot) pairs by (expert, row, slot) and its inverse. The order is unique, so a parallel sort on a device must give the same permutation.
  3. moe_gather_rows (token rows into expert order, [rows · K x d]) and moe_combine_rows (back, weighted: y_r = w_r0 yp_(r,0) + w_r1 yp_(r,1) + ... in slot order, so the combine is deterministic, no atomics), and their backward passes.
  4. grouped_linear: expert e multiplies its segment of the permuted rows by its own matrix, with both backward products in grouped_linear_backward; moe_experts_forward / moe_experts_backward, the experts' MLPs (GELU, ReLU² or SwiGLU, the configuration's mlp) over the permuted rows, with the dense MLP's activation steps.
  5. Shared experts: one dense MLP of shared_experts · expert_d_ff (moe_shared_config), the dense passes of ml/mlp.hpp, added to the routed output.
  6. Balancing: moe_update_bias, moe_balance_loss, moe_z_loss, and moe_load, per-expert load statistics that merge across workers.
  7. The layer: moe_forward and moe_backward compose them; moe_parameter_count, moe_activation_values, moe_activation_indices and moe_gradient_work size its buffers, and moe_weights_in, moe_activations_in and moe_gradients_in lay them out; the overload of mlp_forward for moe_weights is the layer for one token, for decoding. The block with an MoE MLP is ml/moe_block.hpp (with latent attention, ml/composed_block.hpp); expert parallelism across ranks is ml/expert_parallel.hpp.

// The layer over 32 rows (four sequences of 8) learning to map xs to a fixed target by SGD
constexpr std::size_t rows = 32, d = ds.d_model;
std::vector<float> params = noise(ml::moe_parameter_count(ds), 7, 0.3), grads(params.size()), selection(ds.experts, 0.0f);
std::vector<float> values(ml::moe_activation_values(ds, rows)), work(ml::moe_gradient_work(ds, rows));
std::vector<u32> indices(ml::moe_activation_indices(ds, rows));
const auto xs = noise(rows * d, 8, 1.0), target = noise(rows * d, 9, 0.5);
std::vector<float> ys(rows * d), dys(rows * d), dxs(rows * d);
const auto act = ml::moe_activations_in<ds>(std::span<float>(values), std::span<u32>(indices), rows);
const auto g = ml::moe_gradients_in<ds>(std::span<float>(grads), std::span<float>(work), rows);
auto step = [&] {
const auto w = ml::moe_weights_in<ds>(std::span<const float>(params), std::span<const float>(selection));
const auto aux = ml::moe_forward<ds>(backend, w, xs, ys, act, 4);
float loss = aux.balance + aux.z;
for (std::size_t i = 0; i < ys.size(); ++i) {
const float e = ys[i] - target[i];
loss += 0.5f * e * e / rows;
dys[i] = e / rows;
}
std::fill(grads.begin(), grads.end(), 0.0f);
ml::moe_backward<ds>(backend, w, xs, act, dys, dxs, g, 4);
for (std::size_t i = 0; i < params.size(); ++i)
params[i] -= 0.5f * grads[i];
ml::moe_update_bias<ds>(backend, act.counts, std::span<float>(selection)); // the load, toward uniform
return loss;
};

float last = first;

The arithmetic, exactly (so that a device can match it). Every product and sum is its own statement (no fused multiply-add; GCC needs -ffp-contract=off, see ml/quantize.hpp), in T.

  • Routing, per row z (logits) and selection bias b (or none): the affinities s are z itself (softmax_top_k), softmax(z) (softmax, ml/softmax.hpp's own) or sigmoid(z_e) (sigmoid); the key is s_e + b_e (or s_e); the chosen experts are top_k<K> of the keys (ml/sampling.hpp: largest first, ties to the lower index). With node-limited routing (expert_groups G, group_top_k J; DeepSeek-V3's n_group and topk_group), group g holds experts [g·E/G, (g+1)·E/G), its score is k_0 + k_1, its two largest keys (top_k<2>, the larger first; k_0 alone for groups of one), the J groups of the largest scores are kept (top_k<J>), and top_k<K> runs over their experts' keys in expert order. Weights, slot i of expert e_i: softmax_top_k, m the largest chosen logit, u_i = exp(z_(e_i) - m), S = u_0 + u_1 + ... in slot order, w_i = (u_i / S) · scale; softmax, w_i = p_(e_i) · scale; sigmoid, S the sum of the chosen s in slot order, w_i = (s_(e_i) / S) · scale.
  • The combine: y = w_0 · yp_0, then y = y + w_i · yp_i for i = 1 .. K-1; its backward dyp_i = w_i · dy and dw_i = sum_j yp_i[j] · dy[j] from 0 in j order; the gather's backward dx = dx + dxp_i for i = 0 .. K-1.
  • The grouped products: each expert's segment is linear_sequence (one gemm), experts in order; on core's reference backend a row's output depends only on that row, and an expert's weight gradient sums its segment's rows in permuted order.
  • The balance loss over S groups of T = rows / S rows (a group is a sequence: S = 1 is Switch's batch-wise loss, one per sequence DeepSeek-V3's sequence-wise one), with D the denominator (S unless given): f_e = c_e / (T · K) from the group's counts, P_e = (sum_t p_te) / T summed in row order, the group's L = (alpha · E) · sum_e f_e P_e in expert order, the loss (sum of the groups' L in order) / D; the gradient in p_te is ((alpha · E) · f_e) / (T · D), taken through the softmax (or the normalised sigmoid) to the logits.
  • The z-loss over rows rows with denominator D (rows unless given): beta · (sum_t lse_t²) / D in row order; the gradient in z_tj is ((2 · beta) · lse_t / D) · softmax(z_t)_j.

Relationships. ml/mlp.hpp (moe_gate, the per-token router; the dense MLP passes, reused), ml/linear.hpp (linear_sequence, the products), ml/softmax.hpp, ml/sampling.hpp (top_k), ml/transformer_config.hpp (the expert fields), ml/moe_block.hpp, ml/expert_parallel.hpp; the plan, TRAINING.md T10. Group: snicholls-core.

Implementations. One, for any backend, on the host. The grouped product loops linear_sequence over the experts; a device library replaces it by one grouped kernel.

Guarantees. constexpr, no allocation (a row's affinities and keys are std::arrays of E), deterministic: the same inputs give the same bits whatever the backend's scheduling, because every reduction's order is stated above. Routing is O(rows · E · K), the permutation O(rows · K + E), gather and combine O(rows · K · d), the experts' MLPs the dense MLP's work for rows · K rows. Weight gradients are added into; the activations' gradients are written, except the layer's input gradient, which is added into (TRAINING.md T3). moe_load is trivially copyable and merges.

Errors. Preconditions, asserted: every span has the size its documentation gives, expert ids are below E, the rows divide into the groups. An invalid configuration, or a dense one where experts are needed, is a compile error.

Performance. The grouped product, the gather and the combine through linalg::reference against the same loops by hand, after a bit-for-bit fairness check (benchmarks/ml/moe_benchmark.cpp): 256 tokens of 256 routed to 4 of 16 experts, each expert's up projection 128 x 256 (Release, Apple clang 17, Xeon W-3245, macOS 26, 2026-11-19, medians of five, a shared machine at load average about 12):

Step Core By hand
grouped_linear, 1024 rows 30.0 ms 29.6 ms
moe_gather_rows 38.6 us 38.7 us
moe_combine_rows 41.0 us 40.5 us

Level: the views, the segments and the backend's dispatch cost nothing measurable. The reference product is a plain loop; a BLAS or a device backend is where the grouped product gets fast.

Tests and demos. tests/ml/moe_test.cpp, demos/ml/moe_demo.cpp.

Dependencies. <array>, <cassert>, <concepts>, <cstddef>, <cstdint>, <span>, <type_traits>, linalg/backend.hpp, math/constexpr_math.hpp, ml/activations.hpp, ml/linear.hpp, ml/mlp.hpp, ml/row.hpp, ml/sampling.hpp, ml/softmax.hpp, ml/transformer_config.hpp.

Known issues. Expert capacity (dropping tokens past a fixed number per expert, as Switch does) is not implemented: every chosen pair is computed, so the segments' sizes vary with the routing. The selection bias has no gradient by design; it is state the caller keeps beside the weights.

Status. Experimental, new in 0.16.0.

DeepSeek-V3's auxiliary-loss-free balancing: bias_e += gamma · sign(mean load - load_e) with gamma the configuration's bias_update_rate.

The sign is decided in integers, sign(total - E · counts[e]), so it is exact: an expert above the mean load is made less likely to be chosen, one below more, one at it is left alone. The bias enters only the choice. Call it once per step with the step's counts summed over every worker, so every worker keeps the same bias; or, on one worker (or within a DiLoCo round, whose end averages the biases), after every micro-batch with that micro-batch's counts, which undoes the early collapse of routing (every token sent to the same experts while the residual stream is one direction) as many times faster as there are micro-batches a step, in steps of the same gamma.
