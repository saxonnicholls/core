Detailed Description

The backup capability of a store, static form: kv_backup<S> (checkpoint, verify) and its reports.

Overview. Two operations a store with durable data offers to the process that guards it: checkpoint(destination) makes a consistent copy of the whole store at destination while writes go on (RocksDB's Checkpoint, SQLite's VACUUM INTO, a file copy), and verify() checks the stored data (checksums, structure, order) and reports what it found. A run that must be reproduced against a state that has since changed records the checkpoint's sequence beside the store's kv_digest_v1.

// Verify first, then checkpoint; record (sequence, digest) so a later run can prove it reads the same state.
template <typename S>
requires kv_backup<S> && key_value_store<S>
bool nightly(S& store, std::string_view destination)
{
const auto check = store.verify();
if (check.is_err() || !check->ok())
return false;
const auto taken = store.checkpoint(destination);
if (taken.is_err())
return false;
const auto digest = kv_digest_v1(store);
std::printf(" %.*s: %llu keys verified, checkpoint at sequence %llu (%llu bytes), digest %s\n",
static_cast<int>(destination.size()), destination.data(),
static_cast<unsigned long long>(check->keys_checked), static_cast<unsigned long long>(taken->sequence),
static_cast<unsigned long long>(taken->bytes.value_or(0)),
digest.is_ok() ? std::string(digest->hex().view()).c_str() : "-");
return true;
}

What a backup is for stays above core: schedules and retention (asoMonoRepo1's BackupPolicy), uploading a checkpoint elsewhere, restoring one (opening a store at that destination is a backend's constructor). Logical point-in-time views are snapshot() of the store contract. Dumping to JSON is a scan plus a codec, above core.

Relationships. The virtual twin is kv_backup_interface (interfaces/kv_backup.hpp), with adapters both ways; the reference implementation is reference_key_value_store, which keeps checkpoints in memory; the kit is run_kv_backup_conformance (interfaces/key_value_store_conformance.hpp). Group: snicholls-core.

Implementations / variants. reference_key_value_store; the backends above core.

Guarantees. A checkpoint is consistent: it holds the state of one moment, whose sequence it reports. Checkpointing changes nothing in the store. A destination that already holds a checkpoint is refused, never overwritten. verify() changes nothing. No exception crosses either.

Errors. kv_errc::invalid_argument for an empty destination or one that exists; io, unavailable and the rest for storage failures. A verify() that ran and found damage is a success whose report has problems > 0; an error means the check itself could not run.

Examples. See the overview.

Performance. Not benchmarked: backend-specific, from O(1) (hard links) to a full copy.

Tests and demos. tests/concepts/kv_backup_test.cpp, demos/concepts/kv_backup_demo.cpp.

Dependencies. <concepts>, <cstdint>, <optional>, <string_view>, and concepts/key_value_store.hpp.

Known issues. The destination is text whose meaning is the backend's (a directory, a file, a name).

Status. New in 0.22.0. Experimental.
