Detailed Description

snicholls::remote_files_interface: the pure virtual twin of remote_files, and the adapters both ways.

Overview. When the drop is chosen at run time (configuration names SFTP for one counterparty and HTTPS for another), the collector holds a remote_files_interface&. Its pure virtual functions are the operations of the concept remote_files (concepts/remote_files.hpp, where the contract and its value types are documented), so the interface models the concept itself. remote_files_adapter<S> puts any model behind the interface, owning it (S) or referring to it (S&); remote_files_ref is a copyable, non-owning handle on the interface that models the concept.

std::unique_ptr<remote_files_interface> chosen = std::make_unique<remote_files_adapter<memory_remote_files>>(std::move(read_only));
remote_files_ref handle{*chosen}; // copyable, models the concept
std::size_t received = 0;
const auto digest = handle.fetch("in/a.csv", [&](std::span<const std::byte> c) -> capability_result<void> {
received += c.size();
return ok();
});

Relationships. concepts/remote_files.hpp, interfaces/remote_files_reference.hpp, interfaces/remote_files_conformance.hpp. Group: snicholls-core.

Implementations / variants. remote_files_adapter<S> over any model; an implementation above core may derive from the interface directly.

Guarantees. The adapters add one virtual call and nothing else; thread safety is the wrapped implementation's.

Errors. As the contract.

Performance. One virtual call; not benchmarked (a drop is I/O bound).

Tests and demos. tests/interfaces/remote_files_test.cpp (the kit through every form), demos/interfaces/remote_files_demo.cpp.

Dependencies. <string_view>, <type_traits>, <utility>, <vector>, concepts/remote_files.hpp.

Known issues. None.

Status. New in 0.27.0. Experimental until two real implementations pass the kit.
