Detailed Description

snicholls::sql_connection: one connection to an SQL engine; statements, queries, transactions, all returning sql_result.

Overview. The engine half of the SQL contract (the text half is concepts/sql_dialect.hpp):

  • c.dialect(): the engine's dialect, so engine-neutral code generates its SQL through it and runs it here;
  • c.prepare(sql): parse and cache a statement (statements are cached by text, so this is optional: it surfaces a syntax_error or undefined_object before any data is bound);
  • c.execute(sql, params): run one statement, returning the rows it changed;
  • c.query(sql, params, visitor): run a query and visit its rows in order (sql_row, valid during the call); the visitor returns false to stop; the result is how many rows it saw;
  • c.execute_batch(sql, width, rows, fill): one statement for rows rows of width parameters, which fill(row, params) writes; all or nothing;
  • c.begin(), c.commit(), c.rollback(), c.in_transaction(): one transaction at a time;
  • c.ping() and c.is_open().

Over it: sql_execute(c, sql, {params...}) and sql_query(c, sql, {params...}, f) (a visitor returning void or bool), and sql_transaction<C>, which rolls back unless committed.

memory_sql_connection db; // SQLite or PostgreSQL in production
const auto after_bhp = book(db, "BHP", 100);
const auto after_cba = book(db, "CBA", 50);
const auto after_bhp_again = book(db, "BHP", 120); // an upsert

The contract (interfaces/sql_connection_conformance.hpp checks it): values round-trip exactly through the six kinds and core's types; a duplicate key is unique_violation and a conflict clause resolves it; a rollback discards and a commit keeps; a nested begin and a commit without one are misuse; the wrong number of parameters is misuse; an unknown table is undefined_object; text the engine does not understand is syntax_error; a batch that fails changes nothing; ranges, orders and limits select what the dialect's SQL says; and no error carries a parameter's value (sql_error::message is a literal).

Relationships. sql_value.hpp, concepts/sql_dialect.hpp; the twin interfaces/sql_connection.hpp, the reference interfaces/sql_connection_reference.hpp (memory_sql_connection), the kit interfaces/sql_connection_conformance.hpp. Group: snicholls-core.

Implementations. memory_sql_connection: an in-memory table store that runs exactly the statements core's generators write (a test double, not an SQL engine). Above core, in crtp: SQLite and PostgreSQL (libpq).

Guarantees. A connection is used by one thread at a time (as sqlite3* and PGconn); a pool above core shares them. A visitor must not use the connection it is called from.

Errors. sql_error, as the contract says; nothing is thrown but std::bad_alloc.

Performance. Not benchmarked here: crtp benchmarks its engines against hand-written sqlite3 and libpq.

Tests and demos. tests/concepts/sql_connection_test.cpp, demos/concepts/sql_connection_demo.cpp.

Dependencies. <concepts>, <cstddef>, <initializer_list>, <span>, <string_view>, <type_traits>, <utility>, concepts/sql_dialect.hpp, function_ref.hpp, sql_value.hpp.

Known issues. No bulk insert (COPY) in the contract: execute_batch is the portable form, and an engine's faster path stays its own.

Status. New in 0.27.0. Experimental until two real implementations pass the kit.
