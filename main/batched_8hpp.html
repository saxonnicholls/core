Detailed Description

Batched factorise-and-solve: n systems of one size as strided views, one status per system, on parallelism the caller provides.

Overview. Many small dense systems of the same size - a million to a hundred million small systems, as in batched kriging-style solves, local regressions or per-cell Gaussian-process updates - are the case a general-purpose solver serves worst: the call overhead and the threading are paid per system. Here a whole batch is one call. The matrices are a rank-3 view (system, row, column) and the right-hand sides a rank-2 (system, row) or rank-3 (system, row, column) view, any strides, so the systems can sit in the caller's own records with gaps between them. Each system is factorised and solved in place, and its outcome is written to status[i]: a singular or indefinite system is reported for that system only, so the caller falls back for it (a smaller neighbourhood, a nugget, a pivoted solver) and keeps the rest.

// One call factorises and solves every block; each block's outcome is its own status.
std::vector<la::status> status(blocks);
const la::batch_view<double, la::layout_right> systems(a.data(), {blocks, m, m});
const la::md_span<double, 2, la::layout_right> weights(rhs.data(), {blocks, m});
const auto failures = la::ldlt_solve_batched(la::reference, systems, weights, std::span<la::status>(status));
// The caller falls back for the blocks that failed, and only for those: here, drop the repeated sample.
for (std::size_t b = 0; b < blocks; ++b)
if (status[b] != la::status::ok)
std::printf(" block %zu: %s, falls back\n", b, status[b] == la::status::singular ? "singular" : "failed");

Core starts no threads. The caller passes an executor: any callable ex(n, f) that calls f(begin, end) on disjoint ranges covering [0, n), in any order and on any threads, and returns when all have run. That is the shape of a thread pool's parallel_for over an index range; inline_executor runs f(0, n) on the calling thread.

// The caller's parallelism: any callable that runs f(begin, end) over [0, n). Core starts no threads.
auto on_four_threads = [](std::size_t n, auto&& f) {
std::vector<std::thread> pool;
for (std::size_t t = 0; t < 4; ++t)
pool.emplace_back([&f, n, t] { f(n * t / 4, n * (t + 1) / 4); });
for (auto& thread : pool)
thread.join();
};
std::vector<double> a2 = a0, rhs2 = rhs0;
std::vector<la::status> status2(blocks);
const auto failures2 = la::ldlt_solve_batched(la::reference, la::batch_view<double, la::layout_right>(a2.data(), {blocks, m, m}),
la::md_span<double, 2, la::layout_right>(rhs2.data(), {blocks, m}),
std::span<la::status>(status2), on_four_threads);

Relationships. linalg/backend.hpp (the backend concepts; backend<B, T> includes batched_backend<B, T>), linalg/reference.hpp (whose batched members are for_each_system over its single-system members), containers::submdspan (one system of a batch). Group: snicholls-core.

Implementations / variants. A backend implements the three members below. A backend that runs a whole batch in one device call (a GPU's batched LU) implements them directly and may ignore the executor (it then says so: it brings its own parallelism); one that solves system by system calls for_each_system with its single-system members, as the reference backend does.

Each returns the number of systems whose status is not ok. Pivots are n * m entries, system i's at [i * m, (i + 1) * m), as cuBLAS's batched LU stores them.

Guarantees. No allocation, no workspace beyond the arguments, no threads of core's own. Each system's factors, solution and status depend on that system's data alone, so with the reference backend the results are bit-for-bit the same for every executor, chunking and thread count (deterministic; tested). The count of failures is taken after the executor returns, from the status span. The executor must call f for every index exactly once; ranges may run concurrently because they touch disjoint systems. A view whose systems overlap in memory is a precondition violation.

Errors. error::aliased (nothing written) when rhs, pivots or status starts where another argument does, and error::dimension_mismatch (nothing written) when the extents do not fit together: a is n x m x m, b is n x m or n x m x k, pivots has n * m entries, status has n. Otherwise the call succeeds and each system's error is its status: singular, not_positive_definite. A system with a non-ok status has unspecified contents in a and b.

Performance. benchmarks/linalg/batched_benchmark.cpp, 10^6 systems with one right-hand side, double, reference backend against the same algorithms written by hand over raw pointers (Release, AppleClang 17, Xeon W-3245, macOS 26, 2026-11-11, on a shared machine with load average 7 to 10; single-threaded):

Dependencies. <concepts>, <cstddef>, <span>, <type_traits>, result.hpp, linalg/types.hpp.

Known issues. The executor's ranges are as fine as it chooses: a pool should hand out ranges of some thousands of small systems, not single ones.

Status. Experimental, new in 0.6.0.
