Detailed Description

The reference lifecycles of securities: a trade, a fund application or redemption, a corporate action and a repo, each a state enumeration with its presentation and a machine in sml's notation.

Overview
A security_fact (concepts/security_provider.hpp) is an immutable event; the state of the object it is about (an order, a dealing request, an action, a repo) is the fold of its facts through one of these tables, kept as the enumerator on the object, so fsm/persist.hpp saves and loads it and the machine is rebuilt after a crash.
Machine States Facts that drive it
trade_lifecycle placed, filled, settling, settled, failed; cancelled before a fill buy / sell (fill), the settlement instruction, settle, settle_failed
dealing_lifecycle requested, priced, issued, settled; cancelled before issue an application or redemption request, the dealing price, the units issued or redeemed on the register, the cash settled
corporate_action_lifecycle announced, ex, record, paid; withdrawn before the record date the announcement, the ex date, the record date (dividend_entitlement), the payment (dividend_paid and friends)
repo_lifecycle open, accruing, closed repo_open / reverse_repo_open, each interest_accrual, repo_close / reverse_repo_close
sm<trade_lifecycle> machine; // placed
order o{1'000};
ok &= machine.process_event(trade_event::fill{}); // a buy fact: the trade date
ok &= machine.process_event(trade_event::instruct{}); // the settlement instruction is in
o.state = machine.current();
snicholls::println(o.state); // Settling, in its colour
snicholls::reference_key_value_store store;
ok &= save(store, "order/2026-11-26/0001", machine, 0).is_ok(); // version 1
sm<trade_lifecycle> after_restart; // another process
const auto version = load(store, "order/2026-11-26/0001", after_restart);
ok &= version.is_ok() && *version == 1 && after_restart.current() == trade_state::settling;
ok &= after_restart.process_event(trade_event::settle{}); // a settle fact, T+2
ok &= save(store, "order/2026-11-26/0001", after_restart, *version).is_ok();

For a redemption, issued is the units cancelled on the register at the dealing price: the register has changed, and the cash is still to settle. Use these tables as they are or as the model for a provider's own; never a switch over the states.

Relationships
fsm/state_machine.hpp (the machine), fsm/persist.hpp (save and load), fsm/diagram.hpp (the tables drawn), fsm/lifecycle.hpp (the payment lifecycle, the model for these), concepts/security_provider.hpp (the facts), meta/attributes.hpp and display.hpp (the presentation). Group: snicholls-core.
Implementations and variants
Four enumerations and four reference tables. A broker's or registry's own states map to them in servers.
Guarantees and contracts
The enumerators are stable: values never change and new ones are appended, so a stored value keeps its meaning. Every enumerator is a state of its table, so every restore of an enumerator succeeds. Colours: grey while nothing has happened or after a cancellation, blue and cyan in progress, green when done (settled, paid, closed), red for a failed settlement. is_final is constexpr and noexcept.
Errors
None here; the machine's errors are fsm_errc.
Examples
sm<dealing_lifecycle> application; // requested before the cut-off
ok &= application.process_event(dealing_event::price{}); // the NAV is struck
ok &= application.process_event(dealing_event::issue{}); // units issued on the register
ok &= application.process_event(dealing_event::settle{}); // the cash settled
sm<dealing_lifecycle> redemption;
ok &= redemption.process_event(dealing_event::price{}) && redemption.process_event(dealing_event::cancel{});
Performance
Not benchmarked on their own: each is a table of a few rows over a one-byte state, as fsm/lifecycle.hpp (benchmarks/fsm/state_machine_benchmark.cpp).
Tests and demos
tests/fsm/securities_test.cpp; demos/fsm/securities_demo.cpp.
Dependencies
<array>, <cstdint>, and core's fsm/state_machine.hpp, colour.hpp, display.hpp, meta/attributes.hpp.
Known issues and gotchas
A settlement that fails is final here: the retry is a new instruction on a new object, as CHESS rolls a failed settlement into the next day's batch. A repo's accruals keep it accruing (a self-transition, which runs the state's exit and entry, as sml's does).
Status
Experimental, new in 0.27.0.
