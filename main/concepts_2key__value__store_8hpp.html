Detailed Description

The key-value store contract, static form: key_value_store<S>, its ranges, batches, errors and digest.

Overview. An ordered map of byte strings to byte strings, as a concept. Storage is chosen by the composition root (in memory, a file, SQL, RocksDB); code written against key_value_store<S> runs on any of them, and inlines on the in-memory one. Keys and values are std::span<const std::byte> (kv_bytes); the free functions kv_get, kv_put, kv_insert, kv_erase, kv_contains, kv_scan, kv_scan_prefix and kv_count accept any one-byte sequence as well (std::string_view, std::string, literals, byte vectors).

// Code written once against the contract: it runs on any backend, and inlines on the in-memory one.
template <key_value_store S>
result<bool, kv_errc> append(S& ledger, std::string_view book, std::size_t n, std::string_view entry)
{
const std::string key = "e/" + std::string(book) + "/" + std::to_string(n);
return kv_insert(ledger, key, entry); // false: someone else already wrote entry n
}

The contract is three concepts, each the one before plus operations:

  • kv_readable<S>: read (zero-copy, a visitor sees the value), contains, scan (a visitor sees each entry of a kv_range in key order and may stop), sequence;
  • kv_writable<S>: plus put, insert (only when absent: the primitive a ledger appends with), erase, erase_range, apply (a batch of kv_writes, all or nothing);
  • key_value_store<S>: plus snapshot(), a read-only view of one consistent state.

kv_digest_v1(store, range) is the named, stable digest of a range (KV_PLAN D20): a run records (sequence, digest) and a later run verifies it reads the same bytes on any backend.

Use it for keyed persistence with ordered scans. Not for relational queries (an SQL layer), nor for typed objects (a codec layered on top, as crtp's object_store).

Relationships. The virtual twin is key_value_store_interface (interfaces/key_value_store.hpp), with adapters both ways; the reference implementation and test fake is reference_key_value_store (interfaces/key_value_store_reference.hpp); the conformance kit is run_kv_conformance (interfaces/key_value_store_conformance.hpp). Separate capabilities: kv_health (concepts/kv_health.hpp), kv_backup (concepts/kv_backup.hpp). Errors are snicholls::result<V, kv_errc> (result.hpp); visitors are snicholls::function_ref (function_ref.hpp); the digest is SHA-256 (hash/sha2.hpp). Group: snicholls-core.

Implementations / variants. In core, reference_key_value_store (a std::map with a byte-wise comparator). Above core: crtp's in-memory, JSON, SQL, RocksDB and base-encode-decode backends; the database backends of the products. Each documents its own complexity and thread safety.

Guarantees. Every implementation promises, and the conformance kit checks:

  • Order: keys are ordered by unsigned byte-wise comparison, on every backend, with no custom comparator. Empty keys, empty values, embedded NULs and bytes >= 0x80 are all valid.
  • Missing is not an error: read, contains, insert and erase answer false for an absent key; a storage failure is an error (kv_errc), never false or an empty value.
  • Atomicity: every call is atomic; scan sees one consistent state; apply is all or nothing, and a batch that fails (an insert whose key is present, a storage failure) changes nothing, the sequence included.
  • Sequence: sequence() never decreases, never moves on a read or on a call that changed nothing, and increases with every call that changed the store.
  • Snapshot: reads of a snapshot see the state at the moment it was taken, whatever is written later.
  • Exceptions: no exception of the backend crosses the contract: failures are kv_errc values. The only exceptions a call lets out are the caller's own visitor's, unchanged, and the store stays usable after one.
  • Lifetime: bytes passed to a visitor are valid only during the call; a visitor must not call back into the store (copy out what you need).
  • kv_range, kv_write and the comparisons here are constexpr and noexcept. Nothing in the contract forces an allocation: reads and scans hand out views to a visitor.

Errors. kv_errc: unavailable, io, corrupt, read_only, conflict, limit, invalid_argument, out_of_memory, backend. Nothing here throws, except kv_write_batch, which may throw std::bad_alloc while it is being built.

Examples.

// Exactly the keys of one book, in unsigned byte order; then the same keys two at a time.
std::printf(" book cash:\n");
const auto n = kv_scan_prefix(ledger, "e/cash/", [](kv_bytes k, kv_bytes v) {
std::printf(" %s = %s\n", text(k).c_str(), text(v).c_str());
});
const kv_range book = kv_range::prefixed(kv_bytes_of("e/cash/"));
std::string last;
std::size_t chunks = 0, seen = 0;
for (kv_range rest = book;; rest = book.after(kv_bytes_of(last))) {
std::size_t in_chunk = 0;
static_cast<void>(ledger.scan(rest, [&](kv_bytes k, kv_bytes) {
last = text(k);
return ++in_chunk < 2;
}));
if (in_chunk == 0)
break;
++chunks;
seen += in_chunk;
}

Performance. The contract costs nothing on the static path; the virtual path's cost on the in-memory reference is measured in benchmarks/interfaces/key_value_store_benchmark.cpp (BENCHMARKS.md).

Tests and demos. tests/concepts/key_value_store_test.cpp, demos/concepts/key_value_store_demo.cpp; the kit through both forms in tests/interfaces/key_value_store_test.cpp.

Dependencies. <algorithm>, <array>, <concepts>, <cstddef>, <cstdint>, <memory>, <optional>, <span>, <string>, <string_view>, <type_traits>, <utility>, <vector>, and core's function_ref.hpp, result.hpp, reflect/string_access.hpp, hash/sha2.hpp (for the digest).

Known issues. kv_digest_v1 is named crtp.kv.digest.v1 on the wire, the name agreed with its first consumers before it moved into core; the name's meaning never changes, and a new definition gets a new name. Thread safety is a property of each implementation: the reference is not synchronised.

Status. New in 0.22.0; kv_encoded_key in 0.27.0. Experimental until two real implementations pass the kit.
