Detailed Description

snicholls::ml quantised weights: ggml's type ids and block traits, and its 32-element blocks (Q4_0, Q4_1, Q5_0, Q5_1, Q8_0, Q8_1, MXFP4) with NVFP4, Q1_0, Q2_0, F8_E4M3 and the Q8_K activations, byte for byte as ggml lays them out, with quantisation (and its importance-weighted form), dequantisation and the integer dot products, plus symmetric int8 rows.

Overview. A quantised model stores its weights in blocks, each block a few numbers with one or two scales. These are the formats llama.cpp and gpt-oss ship, so a GGUF tensor of one of them is an array of these structs, read in place:

Block Elements Scale Codes Bytes Bits per weight
block_q4_0 32 float16 d = (signed value of largest magnitude) / -8 4-bit x / d + 8, element j low nibble of byte j, j + 16 high 18 4.5
block_q4_1 32 float16 d = (max - min) / 15, m = min 4-bit (x - m) / d 20 5
block_q5_0 32 as Q4_0 with -16 5-bit, the fifth bits in qh 22 5.5
block_q5_1 32 as Q4_1 with 31 5-bit, the fifth bits in qh 24 6
block_q8_0 32 float16 d = amax / 127 int8 round(x / d) 34 8.5
block_q8_1 32 as Q8_0, and s = d · sum q int8 36 9
block_mxfp4 32 E8M0 e = floor(log2 amax) - 2 + 127 FP4 E2M1, packed as Q4_0 17 4.25
block_nvfp4 64 four UE4M3 scales, one per 16 FP4 E2M1 36 4.5
block_q1_0 128 float16 mean abs the sign bit 18 1.125
block_q2_0 64 float16 amax 2-bit round(x / d) + 1, {-1, 0, 1, 2} 18 2.25
block_q8_k 256 float amax / 127, sums of 16 int8 292 9.125
float8_e4m3 rows 1 none OCP E4M3, saturating 1 8

The super-block formats are in ml/quant_k.hpp (Q2_K to Q6_K), ml/quant_iq.hpp (the IQ family) and ml/quant_ternary.hpp (TQ1_0, TQ2_0); they follow the same contract:

  • every block has type (its ggml_type), elements and dot_block (the activation block ggml pairs it with), so quantized_block<B> and block_traits<B> describe it, and ggml_type_traits(id) describes any id a GGUF file holds, at compile time;
  • quantize_row(x, importance, blocks) is ggml's quantize_<type> for one row: importance empty is ggml's reference (quantize_row_<type>_ref), non-empty the importance-matrix path, which minimises the error weighted by it (n_per_row is the row's length, which some formats' weighting reads);
  • dequantize_row(blocks, x) is dequantize_row_<type>, and dot(weights, activations) is ggml's scalar ggml_vec_dot_<type>_<dot type>_generic;
  • quantize(x, blocks), quantize(x, importance, blocks) and dequantize(blocks, x) take any row.
// One row of 64 weights and 64 activations: two blocks of 32 each
std::array<float, 64> w{}, a{};
for (std::size_t i = 0; i < 64; ++i) {
w[i] = 0.05f * std::sin(0.7f * static_cast<float>(i));
a[i] = std::cos(0.3f * static_cast<float>(i));
}
// The weights in three formats, byte for byte as a GGUF file stores them
std::array<ml::block_q8_0, 2> w8{};
std::array<ml::block_q4_0, 2> w4{};
std::array<ml::block_mxfp4, 2> wm{};
ml::quantize(w, std::span(w8));
ml::quantize(w, std::span(w4));
ml::quantize(w, std::span(wm));
// The activations quantised on the fly to Q8_0, then integer dot products, one multiplication per block
std::array<ml::block_q8_0, 2> a8{};
ml::quantize(a, std::span(a8));
const float d8 = ml::dot(std::span<const ml::block_q8_0>(w8), a8);
const float d4 = ml::dot(std::span<const ml::block_q4_0>(w4), a8);
const float dm = ml::dot(std::span<const ml::block_mxfp4>(wm), a8);

quantize_int8(x, q) and dequantize_int8(q, scale, x) give one symmetric scale for a whole row (per-channel or per-tensor int8), the same rounding as Q8_0.

Relationships. ml/minifloat.hpp (float16, float8_e4m3, the E2M1 elements); ml/row.hpp; ml/linear.hpp (quantized_weights over any quant_block); ml/quant_k.hpp, ml/quant_iq.hpp, ml/quant_ternary.hpp, which build on the helpers here. Group: snicholls-core.

Implementations. One per block. The blocks are the formats; the dot products are the scalar reference, which a SIMD or GPU kernel reorders.

Guarantees. constexpr, no allocation, linear in the row. The blocks are trivially copyable, have ggml's sizes and no padding (static_asserted against ggml_type_traits). Quantised bytes equal ggml's and dot products equal ggml's _generic ones on every input of the committed fixtures (tests/fixtures/ml/, from scripts/generate_quant_fixture.cpp and scripts/generate_quant_formats_fixture.cpp, built against ggml). Each multiplication and each addition is its own statement, so no compiler fuses them into an FMA and the result is the same on every machine.

Errors. Preconditions, asserted: the row has elements · blocks.size() numbers; importance is empty or as long as the row; the rows of a dot product have the same number of blocks. NaN and infinity are not representable in these formats; the result is unspecified, as in ggml (deterministic, but not meaningful).

Performance. Against ggml's scalar loops written out by hand (benchmarks/ml/quantize_benchmark.cpp), rows of 4,096: the three dot products level, 1.9 to 2.6 billion weights per second; Q8_0 quantisation 2x faster than ggml's loop (590 against 300 million per second), from rounding without roundf (Xeon W-3245, Release, Apple clang 17, 2026-11-11, one thread, scalar code; SIMD kernels are the libraries' above). The formats new in 0.17.0 are in BENCHMARKS.md.

Tests and demos. tests/ml/quantize_test.cpp, demos/ml/quantize_demo.cpp.

Dependencies. <array>, <bit>, <cassert>, <cstddef>, <cstdint>, <limits>, <span>, <string_view>, <type_traits>, snicholls/core/math/constexpr_math.hpp, ml/minifloat.hpp, ml/row.hpp.

Known issues. ggml computes MXFP4's exponent as floorf(log2f(amax)), which depends on the C library and can round up for an amax a few units in the last place below a power of two; core reads the exponent from the bits, as the OCP specification defines it. Where ggml converts a float out of an integer's range (C leaves it undefined: the inverse scale of a block of subnormals is infinite; an MXFP4 amax below 2^-125 makes a negative exponent), core gives what ggml gives on x86, where the fixtures were made (cvttss2si's INT_MIN, then the low byte). NVFP4's scale conversion is ggml's (ggml_fp32_to_ue4m3: the rounding bit added, not ties to even), so the bytes are ggml's. ggml leaves Q8_K's bsums unset for a block of zeros; core writes zeros. A dot product over infinities is a NaN whose sign is the hardware's (negative on x86, positive on ARM), so results are bit-identical across platforms except for the sign of a NaN. Each multiply and add is its own statement, which Clang never fuses, but GCC fuses across statements by default in C++ (-ffp-contract=fast), so on a target with FMA (every ARM64) the last bit can differ: compile with -ffp-contract=off for ggml's bits.

Status. Experimental, new in 0.7.0; the type ids, traits, importance weighting and the formats besides Q8_0, Q4_0 and MXFP4 new in 0.17.0.

float snicholls::ml::dot ( std::span< const float8_e4m3 > x,
std::span< const float > y )
constexpr

The dot product of an FP8 E4M3 row with a float row, in the order of ggml's ggml_vec_dot_f8_e4m3_f32 on x86 (SSE3).

ggml's loop is SIMD: per 32 numbers, eight accumulators of four lanes each add their products; the 32 lanes then reduce pairwise (accumulators i and i + 4, then i + 2, then i + 1, then the four lanes as (0 + 1) + (2 + 3)), and the numbers past the last 32 add one by one. That order is the reference here; ggml's order on another SIMD target (NEON, AVX) differs in the last bits.

Parameters
xThe weights.
yThe activations.
Returns
sum x_i · y_i.
