Detailed Description

snicholls::memory_token_verifier: the standard-library reference token_verifier, HS256-tagged tokens it issues itself, for tests only.

Overview. issue(claims) returns a token mt1.<serial>.<tag>, where the tag is the lowercase hexadecimal HMAC-SHA256 (core's hmac<sha256>) of mt1.<serial> under the verifier's key, and remembers the claims. verify recomputes the tag and compares it with the presented one by constant_time_equal, as a real verifier must, then answers the claims; a token whose expires_at is at or before the verifier's clock, or that expire marked, is stale; anything else is unauthorized. fail_next(code, response) makes the next verify fail as though the store it consults had answered response.

It is not a JWT: base64url, JSON and the JWKS are servers' (auth/jwt.hpp), and the EdDSA, ES256 and RS256 checks behind it are crypto's. It needs neither, so a product's route tests run with the standard library alone. Never use it for production tokens.

const utc_s now = utc_s::from_unix_seconds(1'800'000'000);
memory_token_verifier v{secret<std::string>{"a test-only HS256 key of 32 bytes or more"}, manual_utc_clock{now}};
token_claims c;
c.subject = uuid::from_u64(0xa11ce, 1);
c.expires_at = now + std::chrono::minutes{15};
const std::string token = v.issue(c); // mt1.<serial>.<HMAC-SHA256 in hex>
const auto fresh = v.verify(token);
v.clock().advance(std::chrono::minutes{15}); // the verifier owns its clock
const auto later = v.verify(token); // stale: the client refreshes

Relationships. Models token_verifier (concepts/token_verifier.hpp); passes its kit in every form. Group: snicholls-core.

Implementations / variants. One. basic_memory_token_verifier<Clock> reads any utc_clock (time/utc_clock.hpp), owned by value and reached through clock(); memory_token_verifier is basic_memory_token_verifier<manual_utc_clock>.

Guarantees. verify is const; it is safe to call concurrently once the tokens are issued and no failure is armed (issue, expire and fail_next are not). Errors carry fixed messages only: never the token, never the key. The key is held as a snicholls::secret.

Errors. unauthorized ("the token does not verify"), stale ("the token has expired"), and whatever fail_next armed.

Performance. benchmarks/interfaces/token_verifier_reference_benchmark.cpp: verify against the same HMAC and compare written by hand. Not yet quoted from a quiet machine: make benchmarks records them in BENCHMARKS.md.

Tests and demos. tests/interfaces/token_verifier_reference_test.cpp, demos/interfaces/token_verifier_reference_demo.cpp.

Dependencies. <charconv>, <chrono>, <concepts>, <cstddef>, <cstdint>, <optional>, <string>, <string_view>, <system_error>, <utility>, <vector>, hash/hmac.hpp, hash/secure.hpp, hash/sha2.hpp, secret.hpp, interfaces/token_verifier.hpp, time/utc_clock.hpp.

Known issues. Claims are held in memory for the verifier's life; it is a test fixture.

Status. New in 0.27.0; the clock a utc_clock template parameter, owned, since 0.27.0 (it was a std::function<utc_s()>).
