Detailed Description

SHA3-224/256/384/512 and SHAKE128/256 (FIPS 202), and Ethereum's Keccak-256, on one Keccak-f[1600].

Overview. The Keccak sponge: a 1600-bit state, permuted by keccak_f1600, absorbing input rate bytes at a time and squeezing output the same way. The hashes differ only in their rate and their padding byte:

Name Rate (bytes) Padding Output
sha3_224 / sha3_256 / sha3_384 / sha3_512 144 / 136 / 104 / 72 0x06 (FIPS 202) 28 / 32 / 48 / 64 bytes
shake128 / shake256 168 / 136 0x1F any length (an extendable-output function)
keccak256 136 0x01 (Keccak's submission, before FIPS 202) 32 bytes

keccak256 is not SHA3-256: Ethereum adopted Keccak before NIST changed the padding, so addresses, function selectors, event topics, storage slots and EIP-712 hashes are Keccak-256, and a SHA3-256 in its place gives a different, silently wrong, answer. Every function is constexpr, so a function selector is a compile-time constant:

// A function selector is the first four bytes of Keccak-256 of the signature: a constant, so a dispatch table
// over calldata is a switch
constexpr std::uint32_t selector(std::string_view signature) noexcept
{
const auto h = snicholls::keccak256::hash(signature);
return (static_cast<std::uint32_t>(h[0]) << 24) | (static_cast<std::uint32_t>(h[1]) << 16) |
(static_cast<std::uint32_t>(h[2]) << 8) | static_cast<std::uint32_t>(h[3]);
}
const char* method(std::uint32_t calldata_selector) noexcept
{
switch (calldata_selector) {
case selector("transfer(address,uint256)"): return "transfer";
case selector("approve(address,uint256)"): return "approve";
case selector("balanceOf(address)"): return "balanceOf";
default: return "unknown";
}
}
// Keccak-256 is not SHA3-256: the padding differs, and so does every digest
static_assert(snicholls::keccak256::hash("") != snicholls::sha3_256::hash(""));

The fixed-length hashes have the incremental interface of every hash in core (update, finish) and a one-shot hash. SHAKE has update, then squeeze(out) any number of times for any lengths (the stream is the same however it is cut), finish<N>() for one digest<N>, and hash<N>(input).

Relationships. digest<N> and hash_input (hash/digest.hpp); hmac<sha3_256> (hash/hmac.hpp), whose block size is the rate; uint256 (uint256.hpp) for the amounts an ABI word carries. Group: snicholls-core.

Implementations / variants. One sponge, keccak_sponge<Rate, Pad, Digest>; the names above are its aliases, and keccak_xof<Rate> is the same sponge squeezing without a fixed length.

Guarantees. Every member is constexpr and noexcept; no allocation; a hasher is a trivially copyable value (208 bytes of state and buffer, a little more for the rate). Complexity: one permutation (24 rounds) per rate bytes absorbed or squeezed. After finish, or for SHAKE after the first squeeze, update must not be called again.

Errors. None.

Examples. Above; demos/hash/sha3_demo.cpp.

Performance. benchmarks/hash/sha3_benchmark.cpp: Keccak-256 and SHA3-256 against a hand-written sponge and OpenSSL (when installed), after a fairness check. Release, Apple clang 17, Xeon W-3245 (a shared machine), 2026-11-20, 16 KiB / 64-byte messages: Keccak-256 core 315 / 139 MB/s, the hand sponge 198 / 91; SHA3-256 core 319 / 137, OpenSSL 423 / 91. (OpenSSL 3 before 3.2 has no KECCAK-256; the row is skipped where it is missing.)

Tests and demos. tests/hash/sha3_test.cpp (FIPS 202's examples, NIST's byte-oriented short-message and Monte Carlo vectors for SHA-3 and SHAKE, Ethereum's well-known Keccak-256 values, Python's hashlib and PyCryptodome's Keccak on random lengths, every split, every squeeze split), demos/hash/sha3_demo.cpp.

Dependencies. <array>, <cstddef>, <cstdint>, <span>, hash/digest.hpp.

Known issues. cSHAKE, KMAC, TupleHash and ParallelHash (SP 800-185) are not provided. SHAKE's security is capped by its capacity (128 or 256 bits) whatever the output length.

Status. New in 0.17.0. Experimental.
