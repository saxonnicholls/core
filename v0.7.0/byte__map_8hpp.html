Detailed Description

containers::byte_map_view and containers::byte_map: byte strings to 32-bit values in one flat table of 16-byte slots, with a lookup split in two so a batch of them overlaps its cache misses.

Overview. A hash table from byte strings (std::string_view) to std::uint32_t values, built once and then read, laid out for the inner loop of a tokenizer: one flat array of 16-byte slots, linear probing, at most half full. Each slot holds the first eight bytes of its key as a word (the head), its value and its length, so a key of eight bytes or fewer, which is most of a BPE vocabulary, is compared as one word and a length and the slot is the only memory a lookup touches. Longer keys compare their remaining bytes against an arena. An optional reverse table gives the key of a value, which is what decoding needs.

A lookup is split in two: probe(key) hashes the key and prefetches its slot, find(key, probe) finishes it. Probing a batch of keys and then finding them lets the cache misses of a table larger than L2 overlap instead of queueing one behind the other. operator() does both and returns byte_map_no_value for a miss, so a map is an ml::bpe_vocabulary as it stands.

Use it for a vocabulary or any dictionary of short byte strings that is built once and read often, from many threads. Do not use it for a map that changes after it is built (there is no erase), for values that are not 32-bit, or for a table known when the program is written (perfect_map probes nothing).

// A vocabulary built by the compiler: 16 slots, 32 bytes of keys, a reverse table for values 0 .. 7
constexpr containers::byte_map<16, 32, 8> vocab{std::array<std::pair<std::string_view, std::uint32_t>, 6>{
{{"l", 0}, {"o", 1}, {"w", 2}, {"lo", 3}, {"low", 4}, {"ow", 5}}}};
// It is an ml::bpe_vocabulary as it stands
std::array<std::uint32_t, 8> tokens{};
std::array<snicholls::ml::bpe_part, snicholls::ml::bpe_scratch_size(5)> scratch{};
const auto n = snicholls::ml::bpe_encode_piece("lowow", vocab, tokens, scratch).unwrap(); // [low][ow]
// Decoding reads the reverse table
std::string text;
for (std::size_t i = 0; i < n; ++i)
text += vocab.key_of(tokens[i]);

Relationships. ml/bpe.hpp (operator() is its vocabulary), containers/perfect_map.hpp and containers/static_map.hpp (tables known at compile time), hash/wyhash.hpp (the hash), result.hpp (the errors). Group: snicholls-core.

Implementations. Two, with one lookup. byte_map_view works over three spans the caller owns (slots, key arena, reverse table), so a table of any size lives where the caller puts it: the heap, a memory map, static storage. byte_map<Slots, ArenaBytes, Values> owns fixed-size arrays of the same three, so a small table is built by the compiler (its consteval constructor) or placed in static storage with no allocation at all.

Guarantees. No allocation, no exceptions at run time. insert and build are constexpr and noexcept, with the strong guarantee: a failed insert leaves the map as it was. Lookups are constexpr, noexcept and const, so a built map is read from any number of threads at once with no synchronisation; inserting while another thread reads is a data race. A lookup is expected O(1): at most half the slots are full. A view does not own its spans; they must outlive it, and it clears them when it is constructed. Keys are copied into the arena; the caller's key strings need not outlive the map. The hash is machine-independent (wyhash over the bytes in order), so a table built on one machine probes the same slots on another.

Errors. insert and build return result<void, byte_map_error>: too_full (the insert would make the table more than half full), duplicate (the key, or with a reverse table the value, is already in the map), key_too_long (more than 255 bytes), arena_full (the key's bytes do not fit the arena, or the arena would pass 16 MB), bad_value (the value is byte_map_no_value, or with a reverse table is not below its size). build stops at the first failure, keeping the entries before it. The consteval constructor of byte_map makes a failure a compile error. Lookups do not fail: a miss is byte_map_no_value.

Performance. benchmarks/containers/byte_map_benchmark.cpp: 65,536 lookups, half hits and half misses (a key with a byte added, or two keys glued, as a BPE merge asks), against std::unordered_map<std::string_view, std::uint32_t> and an open-addressing table written by hand ({string_view, value} slots at the same load, the whole key hashed with wyhash); a fairness check refuses to run unless all four agree. Release, Apple clang 17, Xeon W-3245, 2026-11-12, median of 3:

512 keys (the BPE fixture) 100,000 keys (4 MB of slots)
byte_map, operator() 921 us 2.06 ms
byte_map, probe 32 then find 990 us 1.68 ms
open addressing by hand 1.24 ms 2.05 ms
std::unordered_map 2.04 ms 6.81 ms

A table in L1 is 1.35x faster than the hand-written one (the head word answers most keys without touching the arena). A table past L2 is memory-bound and level with it one lookup at a time; the batched probe-then-find is what wins there, 1.2x the hand-written table and 4x std::unordered_map. In ts-moveables' BPE encoder (cl100k, 100,256 tokens) the batched lookup took serial encoding of 12.3 MB from 253 to 179 ms.

Tests and demos. tests/containers/byte_map_test.cpp, demos/containers/byte_map_demo.cpp.

Dependencies. <array>, <bit>, <cstddef>, <cstdint>, <span>, <stdexcept>, <string_view>, <type_traits>, <utility>, hash/wyhash.hpp, result.hpp.

Known issues. Keys are at most 255 bytes and the arena at most 16 MB (the slot packs a 24-bit offset and an 8-bit length). byte_map_no_value cannot be stored. The prefetch is GCC's and Clang's __builtin_prefetch; on MSVC probe only hashes, since core includes no platform header. A byte_map of a large vocabulary is megabytes: give it static storage, never the stack. Clang's default constant-evaluation budget limits a consteval build to a few thousand short keys; -fconstexpr-steps= raises it.

Status. Experimental, new in 0.7.0.
