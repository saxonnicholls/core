Detailed Description

snicholls::ml::bpe_encode_piece, bpe_encode_long_piece and bpe_decode: byte-level BPE, token for token what tiktoken gives, with the vocabulary as the caller's lookup and no allocation.

Overview. Byte-level byte-pair encoding as GPT-2, GPT-4, LLaMA 3 and nanochat use it. A tokenizer first splits text into pieces with a regular expression (the split pattern is the tokenizer's, and lives with it, not here); each piece is then encoded on its own:

  1. If the whole piece is a token, that token.
  2. Otherwise start from its bytes and repeatedly merge the adjacent pair whose concatenation has the lowest rank, the leftmost when ranks tie, until no adjacent pair is a token. The ranks of the remaining parts are the tokens.

This is tiktoken's byte_pair_merge, step for step, so the tokens are tiktoken's (tested against tiktoken and rustbpe on committed fixtures). The vocabulary is a callable rank(std::string_view bytes) -> std::uint32_t, returning bpe_no_rank for bytes that are not a token: a hash map for a large vocabulary, a static_map or perfect_map built by the compiler for a small one (then encoding is constexpr end to end). In tiktoken's formats a token's rank is its id.

// A byte-level vocabulary: the bytes of "lowest", then merges in rank order (as a trainer would emit them).
// A token's rank is its id. A real vocabulary is a hash map; this one is small enough to search.
constexpr std::array<std::pair<std::string_view, std::uint32_t>, 11> vocabulary{{
{"l", 0}, {"o", 1}, {"w", 2}, {"e", 3}, {"s", 4}, {"t", 5}, {" ", 6}, // the bytes
{"lo", 7}, {"low", 8}, {"es", 9}, {"est", 10}, // the merges, lowest rank first
}};
constexpr std::uint32_t rank_of(std::string_view bytes)
{
for (const auto& [b, r] : vocabulary)
if (b == bytes)
return r;
return ml::bpe_no_rank;
}
constexpr std::string_view bytes_of(std::uint32_t id)
{
for (const auto& [b, r] : vocabulary)
if (r == id)
return b;
return {};
}
// Encoding a piece at compile time: "lowest" merges lo, then low, then es, then est.
constexpr auto lowest = [] {
std::array<std::uint32_t, 6> out{};
std::array<ml::bpe_part, ml::bpe_scratch_size(6)> scratch{};
const std::size_t n = ml::bpe_encode_piece("lowest", rank_of, out, scratch).unwrap();
return std::pair{out, n};
}();
static_assert(lowest.second == 2 && lowest.first[0] == 8 && lowest.first[1] == 10);

Relationships. result.hpp (the errors), containers/perfect_map.hpp (a vocabulary built at compile time). Splitting text into pieces, training a vocabulary, and reading tokenizer files belong to the libraries above core. Group: snicholls-core.

Implementations. Two, with the same tokens. bpe_encode_piece rescans the parts for the lowest rank after every merge, as tiktoken does: O(n²), and the fastest there is for the short pieces real text is made of. bpe_encode_long_piece keeps the candidate pairs in a binary heap keyed (rank, start), whose minimum is the pair tiktoken merges (lowest rank, leftmost on ties): O(n log n), for the long piece a split pattern can keep whole (a run of spaces, a minified line, a base64 blob). Use it from bpe_long_piece_threshold bytes.

Guarantees. constexpr when rank is. No allocation: the caller's output and scratch spans. Complexity: bpe_encode_piece O(n²) rank lookups for a piece of n bytes in the worst case, as tiktoken; bpe_encode_long_piece O(n) rank lookups and O(n log n) heap steps. Pure: the same piece and vocabulary give the same tokens on any thread.

Errors. bpe_error::output_too_small (no slot for a piece that is one token, or fewer than piece.size() slots, the most tokens a piece can give, for one that is not), scratch_too_small (fewer than bpe_scratch_size(piece.size()) parts, or bpe_long_scratch_size for bpe_encode_long_piece), unknown_bytes (a single byte is not a token: the vocabulary is not byte-level; out may then be partly written). The size checks come first, so on those out is untouched.

Performance. benchmarks/ml/bpe_benchmark.cpp: against tiktoken's algorithm written out by hand with the same lookup, about 20% faster (no allocation per piece). Against tiktoken and rustbpe themselves, on 12.3 MB of Python source (2.8 million pieces), one thread, Release -O3 -march=native, Apple clang 17, Xeon W-3245, 2026-11-11, with a PCRE2 split and an open-addressing vocabulary around it: cl100k, 9.2 million tokens/s against tiktoken 0.14's 2.3 million (from Python); a 32,768-token vocabulary trained by rustbpe, 11.0 million against tiktoken's 2.7 million and rustbpe 0.1's 0.9 million. Every token agreed with tiktoken's. The merge alone is 19 and 26 million tokens/s; the split is the other half. bpe_encode_long_piece against bpe_encode_piece, cl100k, same machine: 1.2-1.8x slower on the corpus's merged pieces of 5-300 bytes; level at about 1 KB (from about 128 B on letters and punctuation; runs of spaces, which cl100k has long tokens for, catch up last); 13-18x faster at 16 KB; about 100x at 128 KB (a run of spaces, 3.1 s against 32 ms). Hence bpe_long_piece_threshold, 1024: at or past the crossover on every shape measured. benchmarks/ml/bpe_benchmark.cpp (BM_BpeLongPiece_Rescan and _Heap) measures the crossover on random letters with the fixture's vocabulary.

Tests and demos. tests/ml/bpe_test.cpp (tiktoken's and rustbpe's tokens on a committed fixture, tests/fixtures/ml/bpe_fixture.txt, generated by scripts/generate_bpe_fixture.py; and bpe_encode_long_piece against bpe_encode_piece on the fixture, on random pieces dense in ties and on long pieces), demos/ml/bpe_demo.cpp.

Dependencies. <concepts>, <cstddef>, <cstdint>, <span>, <string_view>, snicholls/core/result.hpp.

Known issues. A piece is at most 2^32 - 1 bytes.

Status. Experimental, new in 0.6.0; bpe_encode_long_piece new in 0.6.1.

The rescan of bpe_encode_piece becomes a binary heap of candidate pairs ordered by (rank, start): its minimum is the lowest rank, and among equal ranks the leftmost, the pair tiktoken merges. A merge changes the pair to its left and the pair at its own start; their new ranks are pushed and the old entries are skipped when they surface. An entry is current exactly when its part is alive and its rank is the part's pair rank now: the pair at a start only ever grows, and distinct byte strings have distinct ranks.
