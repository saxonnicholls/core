Detailed Description

snicholls::task_pool_interface: the pure virtual twin of task_pool_like, and the adapters both ways.

Overview. When the pool is held by pointer and chosen at run time (a task graph keeps one, a benchmark swaps them), code holds a task_pool_interface&. Its members are those of task_pool_like (concepts/task_pool.hpp, where the contract is documented), and it satisfies the concept and the trait (asserted below), so a member changed on one side only fails to compile. The adapters:

  • task_pool_adapter<Impl>: the interface implemented by forwarding to a model, held by value, or bound to one when Impl is a reference (a non-owning view);
  • any_task_pool: a value owning a std::unique_ptr<task_pool_interface>, which models the concept, for code that takes pools by value.
std::unique_ptr<task_pool_interface> chosen = std::make_unique<task_pool_adapter<deferred_task_pool>>();
int ran = 0;
chosen->submit([&ran] { ++ran; });
chosen->wait_idle();
any_task_pool value{std::move(chosen)}; // a value that models the concept
value.submit([&ran] { ++ran; });
value.wait_idle();

Relationships. concepts/task_pool.hpp, interfaces/task_pool_reference.hpp, interfaces/task_pool_conformance.hpp. Group: snicholls-core.

Implementations / variants. task_pool_adapter<Impl> over any model; ts-moveables' pools derive from the interface directly.

Guarantees. The adapters add one virtual call and nothing else; thread safety is the wrapped pool's.

Errors. None.

Performance. One virtual call; not benchmarked here (ts-moveables benchmarks its pools).

Tests and demos. tests/interfaces/task_pool_test.cpp (the kit through every form), demos/interfaces/task_pool_demo.cpp.

Dependencies. <cstddef>, <functional>, <memory>, <type_traits>, <utility>, concepts/task_pool.hpp.

Known issues. C++17-clean by rule (snicholls_core_cpp17_check).

Status. New in 0.27.0. Experimental until two real implementations pass the kit.
