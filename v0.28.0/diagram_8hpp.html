Detailed Description

fsm::to_mermaid, to_dot, to_plantuml: a machine's table drawn as Mermaid, Graphviz DOT or PlantUML, generated from the table itself, so the documentation's diagram is the code.

Overview
A table is a specification; these turn it into the three diagram languages a reader is likely to have: Mermaid (rendered by GitHub, GitLab and most documentation sites), Graphviz DOT, and PlantUML (sml's plant_uml example, reproduced). Every row is drawn: initial states as [*] -->, X as [*], guards in brackets, actions after a slash, entry and exit actions and internal transitions on the state, composites as nested states, orthogonal regions separated by --.
const std::string mermaid = to_mermaid<lifecycle>(); // or to_mermaid(machine)

State names come from the state: a "name"_s string, an enumerator's name, or the type's unqualified name. Guards and actions are named by their types: a named function object reads well (guard, send_ack), a lambda is drawn as lambda.

Relationships
fsm/state_machine.hpp (the table). Group: snicholls-core.
Implementations and variants
to_mermaid (stateDiagram-v2), to_dot (a digraph, composites as clusters), to_plantuml (@startuml ... @enduml, as sml's example writes it). Each takes the definition as a template argument or a machine as an argument.
Guarantees and contracts
Pure functions of the table's type: the same table gives the same text on every platform, except for a guard or action named by a compiler-spelled type. Not constexpr (they build a std::string).

Examples
struct e1 {};
struct e2 {};
struct e3 {};
struct e4 {};
struct e5 {};
struct guard {
bool operator()() const { return true; }
};
struct guard2 {
bool operator()() const { return true; }
};
struct action {
void operator()() {}
};
struct action2 {
void operator()() {}
};
struct on_s1_entry {
void operator()() {}
};
struct on_s2_exit {
void operator()() {}
};
struct sub_machine {
auto operator()() const
{
using namespace snicholls::fsm;
return make_transition_table(
*"orth1"_s = X,
*"orth2"_s = X);
}
};
struct plant_uml {
auto operator()() const
{
using namespace snicholls::fsm;
return make_transition_table(
*"idle"_s + event<e1> = "s1"_s,
"s1"_s + event<e2> [!guard{} && guard2{}] / action{} = "s2"_s,
"s1"_s + on_entry<_> / on_s1_entry{},
"s2"_s + event<e3> [guard{} || guard2{}] = "s1"_s,
"s2"_s + snicholls::fsm::on_exit<_> / on_s2_exit{},
"s2"_s + event<e4> / action{} = state<sub_machine>,
state<sub_machine> + event<e5> / (action{}, action2{}) = X);
}
};
Performance
Not benchmarked: run once, when documentation is generated.
Tests and demos

Dependencies
<array>, <cstddef>, <cstdint>, <string>, <string_view>, <type_traits>, and core's fsm/state_machine.hpp.
Known issues and gotchas
Mermaid draws orthogonal regions only inside a composite, so a machine with several regions is drawn as one composite state named after the machine.
Status
Experimental, new in 0.24.0.
