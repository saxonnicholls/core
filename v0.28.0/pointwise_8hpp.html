Detailed Description

snicholls::fn::pointwise{f}: a function that is a value of an algebra, added, scaled, compared and combined with && / || point by point. All constexpr.

Overview. A C++ function can be called; it cannot be added to another function to make a third. Wrapped in pointwise, it can: (f + g)(x) is f(x) + g(x), (2.0 * f)(x) is 2.0 * f(x), (f < g)(x) is f(x) < g(x), and (p && q)(x) is p(x) && q(x), short-circuited. Any operand that is not a pointwise is a constant. The result is a pointwise again, so expressions nest, and the arguments may be many:

// A call spread from two legs, as functions of the spot price, added and scaled like numbers.
constexpr fn::pointwise call_100{[](double s) { return s > 100 ? s - 100 : 0.0; }};
constexpr fn::pointwise call_110{[](double s) { return s > 110 ? s - 110 : 0.0; }};
constexpr auto spread = 2.0 * (call_100 - call_110);
static_assert(spread(90) == 0 && spread(105) == 10 && spread(130) == 20);

It is SXT's operators-as-types idea (symbolic-expression-templates' operators.hpp, an algebra of differential operators) with the symbolic part left behind: here the elements are ordinary callables and the operations are evaluated, not simplified. Composition is fn::compose; repeated application is snicholls::nest. Use it to assemble a payoff from legs, a score from weighted features, or a filter from predicates; write the lambda when the expression is used once.

Relationships. fn::compose, fn::constant, fn::on, fn::lift_a2 (the same through the Reader applicative, functional/state.hpp), snicholls::nest. Group: snicholls-core.

Implementations / variants. One class, pointwise<F>, and one node per operation, a fn closure holding its operands by value: trivially copyable when they are, and with no storage for a stateless operand (f + g of two stateless lambdas is one byte; 2.5 * f is one double).

Guarantees. constexpr. A call's noexcept and type are exactly those of the expression it evaluates. Each operand is called once per call with the same arguments, as lvalues (so an argument is never moved from twice); && and || call the right operand only when needed.

Errors. None of their own.

Examples.

// A screen built from predicates: liquid and tight, or simply cheap.
constexpr fn::pointwise price{[](const instrument& i) { return i.price; }};
constexpr fn::pointwise volume{[](const instrument& i) { return i.volume; }};
constexpr fn::pointwise spread_bp{[](const instrument& i) { return i.spread_bp; }};
constexpr auto screen = ((price * volume >= 1e6) && (spread_bp < 5.0)) || (price <= 1.0);
static_assert(screen(instrument{50, 30'000, 2}) && !screen(instrument{50, 30'000, 8}) && screen(instrument{0.5, 10, 50}));

Performance. The calls inline to the hand-written expression; not benchmarked separately (see benchmarks/functional/combinators_benchmark.cpp for the composition of closures).

Tests and demos. tests/functional/pointwise_test.cpp, demos/functional/pointwise_demo.cpp.

Dependencies. <concepts>, <cstddef>, <functional>, <type_traits>, <utility> and functional/combinators.hpp.

Known issues and gotchas. == and != are not lifted: f == g stays a question about the functions, never a new one. A pointwise holding a lambda that captures by reference refers to what it captured. Inside an fsm table (using namespace snicholls::fsm), &&, || and ! on two pointwise guards are ambiguous with the table's own guard algebra: combine them outside the table and use the result as one guard (demos/fsm/state_machine_railway_demo.cpp). And enter it in the table behind a lambda that takes the event ([](const authorise& a) { return authorisable(a); }): the table reads a guard's parameters from its signature, and Clang 18 crashes deducing them through pointwise's generic call operator.

Status. Experimental, new in 0.27.0.
