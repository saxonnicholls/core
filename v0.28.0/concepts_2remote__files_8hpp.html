Detailed Description

snicholls::remote_files: anything that lists the files of a remote drop, streams one to the caller with its SHA-256, and optionally moves one.

Overview. A bank, a payment network or a broker leaves a file a day in a drop: Australia Post's settlement file over HTTPS with a client certificate, a clearer's statements over SFTP. A collector lists the drop, fetches what is new into its own raw store, verifies it, and may move the original to an archive folder. remote_files is that seam:

  • list(prefix): every file whose name starts with prefix, as remote_file{name, size, modified};
  • fetch(name, sink): the file's bytes, streamed in order to the caller's remote_file_sink, and its file_digest (size and SHA-256 of exactly the bytes the sink received), so the collector verifies what it stored against what was sent;
  • move(from, to): optional, gated by supports(remote_files_op::move).

The raw store, the manifest of what was collected and the schedule are the caller's. This is the concept half of a pair; the pure virtual half is remote_files_interface (interfaces/remote_files.hpp), with the adapter remote_files_adapter<S> and the handle remote_files_ref.

The contract (every implementation; interfaces/remote_files_conformance.hpp checks it):

  • A name is relative to the drop's root: 1 to 255 bytes, segments separated by /, no empty, . or .. segment, no leading or trailing /, no backslash, NUL or control character (is_remote_name). A prefix is empty or the start of a name and may end in / (is_remote_prefix). Anything else is capability_errc::invalid_argument, before any I/O.
  • list returns the matching files sorted by name, each once; an empty drop or no match is an empty list, never an error. size is in bytes; modified is the drop's own modification time, to the second.
  • fetch of a name that is not there is capability_errc::not_found. The sink receives the bytes in order, in chunks of any size, and every byte once. A sink's error stops the fetch and is returned as it is. A fetch that fails may have written a prefix of the file to the sink: the caller discards it.
  • The digest is of exactly the bytes delivered: size their count, sha256 their SHA-256.
  • move of a name that is not there is not_found; onto a name that exists, conflict; on an implementation that does not support it, unsupported, and supports(remote_files_op::move) says so in advance. list and fetch are always supported.
  • Nothing logged or returned contains a file's name, its contents, a credential or the server's response: errors follow the redaction rule of capability_error.hpp.

Relationships. capability_error.hpp, capability_ids.hpp (short_text), function_ref.hpp, hash/sha2.hpp, time/utc.hpp; the twin interfaces/remote_files.hpp, the reference interfaces/remote_files_reference.hpp, the kit interfaces/remote_files_conformance.hpp. Group: snicholls-core.

Implementations. memory_remote_files (interfaces/remote_files_reference.hpp, standard library only: name to bytes and a modification time; for tests). Above core: a local folder and SFTP (system OpenSSH, a pinned host key) in ts-moveables; HTTPS with a client certificate in the servers.

Guarantees. The validators and file_digester are constexpr, noexcept and allocation-free; remote_file and file_digest are trivially copyable. Thread safety is the implementation's.

Errors. capability_error, as the contract says.

Performance. Not benchmarked: a drop is I/O bound. file_digester is SHA-256 (hash/sha2.hpp).

Tests and demos. tests/concepts/remote_files_test.cpp, demos/concepts/remote_files_demo.cpp.

Dependencies. <concepts>, <cstddef>, <cstdint>, <span>, <string_view>, <vector>, capability_error.hpp, capability_ids.hpp, function_ref.hpp, hash/digest.hpp, hash/sha2.hpp, time/utc.hpp.

Known issues. A name is bytes: two names that are the same text in different Unicode normalisations are two files. Modification times finer than a second are truncated by the implementation.

Status. New in 0.27.0. Experimental until two real implementations pass the kit.
