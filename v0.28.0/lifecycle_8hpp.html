Detailed Description

fsm::lifecycle_state: the provider-neutral lifecycle of a payment (requested, pending, confirmed, settled, failed, canceled, expired, reversed), its presentation, and its reference machine.

Overview
Every money movement has a state attached to it, and every provider names its states differently: a card network's authorised and captured, a bank's accepted and booked, a chain's in the mempool and six blocks deep. One vocabulary above them lets notifications, reporting and ageing speak one language across products; each provider's own machine maps its states to these.
  • requested: created by us, not yet sent to the provider;
  • pending: the provider has it and has not answered;
  • confirmed: the provider accepted it; funds are committed but not yet in the account;
  • settled: the funds moved;
  • failed: the provider refused it, or it broke;
  • canceled: withdrawn by us or the customer before it was confirmed;
  • expired: no answer within its validity;
  • reversed: undone after confirmation or settlement (a refund, a chargeback, a chain reorganisation).

lifecycle is the reference machine over it, pending -> confirmed -> settled with the failures and the reversal:

sm<lifecycle> machine; // requested
payment p{12'50};
for (const auto step : {0, 1, 2}) {
const bool moved = step == 0 ? machine.process_event(submit{})
: step == 1 ? machine.process_event(confirm{})
: machine.process_event(settle{});
ok &= moved;
p.state = machine.current(); // pending, then confirmed, then settled
snicholls::println(p.state); // acout reads the state's label and colour
}

Its state is the enumerator, so the machine is rebuilt from the byte stored on the transaction:

sm<lifecycle> later; // another process, another day
ok &= later.restore(p.state).is_ok();
ok &= later.process_event(reverse{}) && later.current() == lifecycle_state::reversed; // a refund
ok &= is_final(later.current()) && !is_final(lifecycle_state::settled);
ok &= !later.process_event(settle{}); // nothing leaves reversed

Use lifecycle_state on any object that moves money, and lifecycle as is or as the model for a provider's own table (its events are the provider's webhooks). Not for the ledger's journal rows, which hold no state: a transition that moves money posts a fact, and the state is the fold of the facts.

Relationships
fsm/state_machine.hpp (the machine), fsm/persist.hpp (save and load the state), fsm/diagram.hpp (the table drawn), meta/attributes.hpp and display.hpp (the presentation: colour, label, tooltip). Group: snicholls-core.
Implementations and variants
One enumeration and one reference table. Providers' tables live with the providers' adapters, above core.
Guarantees and contracts
The enumerators are stable: their values never change and new ones are appended, so a stored value keeps its meaning (fsm/persist.hpp stores the value). Colours, as core's presentation rules say: green for settled (the money arrived), red for failed, grey while nothing has happened (requested, pending, canceled), blue for confirmed, yellow for expired, magenta for reversed. is_final is constexpr and noexcept.
Errors
None here; the machine's errors are fsm_errc.

The payment demo (fsm/lifecycle_payment_demo.cpp) saves and loads the state through the reference key-value store, with a simulated crash and a stale writer; the chain demo (fsm/lifecycle_chain_transaction_demo.cpp) confirms a chain transaction after a number of blocks set by a dependency.
Performance
benchmarks/fsm/state_machine_benchmark.cpp runs the lifecycle against the same machine written by hand: 7.56 ns per random event against 7.49 (macOS x86-64, Apple Clang 17, Release, 2026-11-24, load 9); the same instructions. current() is the stored byte, since the states are numbered by their enumerators.

Known issues and gotchas
