Detailed Description

snicholls::token_verifier: a presented credential in, a verified caller (token_claims) out.

Overview. Every authenticated route asks one question: who presented this token? A token verifier answers it without the route knowing what a token is: a JWT checked against a JWKS (EdDSA, ES256, RS256), an opaque session id looked up in a session store, a hashed API key. The route's authenticate step calls verify and puts the claims in the request's context. This is the concept half of a pair; the pure virtual half is token_verifier_interface (interfaces/token_verifier.hpp), with token_verifier_adapter<V> and token_verifier_ref.

The caller is a party, named by its uuid: the same id the role store keys grants by (concepts/role_store.hpp), so roles.grants_of(claims.subject, tenant, now) needs no translation. The claims' roles are informational: authorisation re-reads them from the role store on every request, so a revocation does not wait for the token to expire. What a role permits is the policy's (servers' role catalogue), not the token's.

The contract (interfaces/token_verifier_conformance.hpp checks it):

  • a valid token gives token_claims naming its party in subject;
  • an unknown, malformed, forged or altered token is capability_errc::unauthorized, the empty token too (an implementation that checks a signature may answer signature_invalid for an altered one);
  • an expired token is capability_errc::stale, so the client refreshes instead of signing in again;
  • verify is const and returns every failure as a value;
  • the token never reaches an error, and neither does a provider's response (a JWKS endpoint's, a session store's): the redaction rule of capability_error.hpp. An implementation never logs the token.
// A route's authenticate step: any verifier, a bearer token in, the party out.
template <token_verifier V>
capability_result<token_claims> authenticate(const V& v, std::string_view authorization)
{
constexpr std::string_view bearer = "Bearer ";
if (!authorization.starts_with(bearer))
return fail(capability_errc::unauthorized, {}, "no bearer token");
return v.verify(authorization.substr(bearer.size()));
}

Relationships. capability_error.hpp, capability_ids.hpp (role_id, permission_id, wallet_address, short_text), uuid.hpp, time/utc.hpp; concepts/role_store.hpp (the authority on roles), concepts/signature_verifier.hpp (what a JWT verifier checks its signature with); the twin interfaces/token_verifier.hpp, the reference interfaces/token_verifier_reference.hpp, the kit interfaces/token_verifier_conformance.hpp. Group: snicholls-core.

Implementations.

  • memory_token_verifier (interfaces/token_verifier_reference.hpp): tokens it issues itself, HS256-tagged with core's hmac<sha256> and checked with constant_time_equal; standard library only, for tests only.
  • Above core: servers' JWT verifier (auth/jwt.hpp: base64url, JSON, the JWKS, the policy that refuses HS256) over a signature_verifier whose EdDSA, ES256 and RS256 checks are crypto's; servers' session-store verifier. Neither JSON, base64 nor elliptic curves are core's.

Guarantees. has_role and has_scope are linear in the claims and allocation-free. Thread safety is the implementation's; a verifier shared by routes must be safe to call concurrently.

Errors. capability_error: unauthorized, stale, signature_invalid, and unavailable (or timeout) when what it consults is down.

Performance. benchmarks/interfaces/token_verifier_reference_benchmark.cpp (the reference's verify).

Tests and demos. tests/concepts/token_verifier_test.cpp, demos/concepts/token_verifier_demo.cpp.

Dependencies. <algorithm>, <concepts>, <cstdint>, <optional>, <string_view>, <vector>, capability_error.hpp, capability_ids.hpp, uuid.hpp.

Known issues. token_claims allocates for its role and scope lists; everything else in it is bounded.

Status. New in 0.27.0, lifted from servers. Experimental until two real implementations pass the kit.
