Detailed Description

BLAKE3: hash, keyed hash, key derivation and extendable output, on one thread, usable at compile time.

Overview. BLAKE3 (O'Connor, Aumasson, Neves, Wilcox-O'Hearn, 2020) is a Merkle tree of 1024-byte chunks, each chunk sixteen 64-byte blocks through a 7-round compression derived from BLAKE2s. One function gives four modes, each a different domain, so their outputs never collide by construction:

  • blake3::hash(input): the 32-byte hash.
  • blake3::keyed_hash(key, input), or blake3{key}: a MAC or PRF under a 32-byte key.
  • blake3::derive_key(context, material), or blake3::key_derivation(context): a key derived from key material under a hard-coded, globally unique, application-specific context string.
  • finish<N>() and finish_into(out, seek): any number of output bytes from any position (an XOF), the first 32 of which are the hash.
// The hash, at compile time
static_assert(snicholls::blake3::hash("").hex().view() == "af1349b9f5f9a1a6a0404dea36dcc9499bcb25c9adc112b7cc9a93cae41f3262");
// Two keys from one secret: each context string is hard-coded and unique to its purpose
struct session_keys
{
snicholls::digest<32> encrypt, authenticate;
};
session_keys derive(const snicholls::digest<32>& shared_secret)
{
return {snicholls::blake3::derive_key("example.org 2026-11-20 session encryption v1", shared_secret),
snicholls::blake3::derive_key("example.org 2026-11-20 session authentication v1", shared_secret)};
}

This is the tree mode run on one thread, with the portable compression: the same outputs as the official implementation, without its SIMD and multithreading. Every function is constexpr.

Relationships. digest<N> and hash_input (hash/digest.hpp); blake2s (hash/blake2.hpp), whose compression it shortens; hkdf_* (hash/kdf.hpp) for key derivation under a standard. Group: snicholls-core.

Guarantees. Every member is constexpr; the unkeyed constructor, key_derivation, update, finish, finish_into and hash are noexcept. No allocation: the chaining-value stack (54 entries, enough for 2^64 bytes) is inside the object, about 1.9 KB. A hasher is a trivially copyable value; finish and finish_into are const, so a hasher can be finished, updated further and finished again. Complexity: one compression per 64-byte block, plus one per parent node (one per chunk, amortised).

Errors. The keyed constructor and keyed_hash throw std::length_error unless the key is exactly 32 bytes; in a constant expression that is a compile error.

Examples. Above; demos/hash/blake3_demo.cpp.

Performance. benchmarks/hash/blake3_benchmark.cpp: against a hand-written single-threaded reference loop, after a fairness check. Release, Apple clang 17, Xeon W-3245 (a shared machine), 2026-11-20, 16 KiB / 64-byte messages: core 1,000 / 602 MB/s, the hand loop 579 / 555 (core compresses whole blocks straight from the input). The official implementation's AVX2 / AVX-512 / NEON paths hash several chunks at once and are several times faster on long inputs.

Tests and demos. tests/hash/blake3_test.cpp (the official test_vectors.json of all three modes, 131 extended bytes each, at every published length from 0 to 102,400; the blake3 Python package on random lengths; every split; seeking), demos/hash/blake3_demo.cpp.

Dependencies. <array>, <cstddef>, <cstdint>, <span>, <stdexcept>, hash/digest.hpp.

Known issues. None known.

Status. New in 0.17.0. Experimental.
