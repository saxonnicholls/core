Detailed Description

fsm::save and fsm::load: a machine's states through any key_value_store, versioned, with compare-and-set so that a stale writer is refused.

Overview
A payment's machine must survive the process that runs it. save(store, key, machine, version) writes every region's state (and every sub-machine's) with the next version; load(store, key, machine) sets the machine back and answers the version it read. A writer that loaded version n and saves while another has already saved n + 1 gets fsm_errc::stale and nothing is written: it reloads and retries, as with any optimistic lock.
sm<outer> machine;
ok &= machine.process_event(go{}) && machine.process_event(dig{});
const auto v1 = save(store, "job/7", machine, 0); // 0: a new key; the result is the version written
ok &= v1.is_ok() && *v1 == 1;
sm<outer> restored; // another process
const auto read = load(store, "job/7", restored); // every region, the sub-machine's included
ok &= read.is_ok() && *read == 1;
ok &= restored.is(state<inner>, "lights on"_s) && restored.is<inner>("deep"_s);
const auto stale = save(store, "job/7", restored, 0); // claims there was nothing: someone saved version 1
ok &= stale.is_err() && stale.unwrap_err_unchecked() == fsm_errc::stale;
ok &= save(store, "job/7", restored, *read).is_ok(); // with the version it read: version 2

The record is text, one line each, readable in any store browser: 

snicholls.fsm.v1
machine lifecycle
version 3
regions 1
3 settled

Each region is a number and a name: the enumerator's value where the machine has a state enumeration (so a record stays valid when enumerators are appended, or renamed), the state's name where it has not (so it stays valid when states are added or reordered).

The compare-and-set is built from the contract's own atomic primitives, so every store has it: a save is one batch of insert(key + "/v/" + version) (which fails if that version exists) and put(key). The versioned keys are the machine's history, one record per save; load_version reads one back.

Use it wherever a machine's state must outlive a process. Not a replacement for storing the state on the object itself (current() is one byte); this is for the machine, and for an audit trail of its states.

Implementations and variants
One format, snicholls.fsm.v1. A new format gets a new name; this one never changes meaning.
Guarantees and contracts
  • save is all or nothing (one apply): on any error nothing is written.
  • load changes the machine only when it succeeds (strong guarantee); no entry or exit action runs.
  • Versions start at 1; save(..., 0) creates. Passing a version other than the one last loaded or saved is a precondition violation (it could create a gap in the history).
  • No exception crosses these functions except std::bad_alloc from building the record and the batch.
Errors
fsm_errc::stale (that version exists: another writer saved first), not_found (nothing under the key), corrupt (the record is not this format), shape_mismatch (a different number of regions), unknown_state (a saved state is not a state of the table), store_unavailable (kv_errc::unavailable), store_failed (any other kv_errc).
Examples
The payment demo, fsm/lifecycle_payment_demo.cpp, crashes a process and restores the payment, and shows a stale writer refused.
Performance
Not benchmarked: a save is one store batch and a record of a few dozen bytes; the store's cost dominates.
Tests and demos
tests/fsm/persist_test.cpp (round trips, the property that a restored machine behaves as the one never saved, every error); demos/fsm/persist_demo.cpp.
Dependencies
<array>, <charconv>, <cstddef>, <cstdint>, <string>, <string_view>, <system_error>, and core's fsm/state_machine.hpp, concepts/key_value_store.hpp (which brings hash/sha2.hpp).
Known issues and gotchas
A machine's history keys sit under its key: a prefix scan of key sees them (key/v/...).
